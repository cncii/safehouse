# 交接项 · 战斗组 → 架构/QA：Godot 引擎自身会把绝对路径写进日志（S10 残余风险）

**提交人**：战斗组（包 C+E）｜**日期**：2026-10-22
**性质**：**不是我们代码的缺陷**，是引擎行为；但对 S10「日志零 PII」有实际影响，需要有人拍板

---

## 一、现象

2026-10-22 实测发现：某个日志文件里有 3 行含**绝对路径**：

```
USER SCRIPT ERROR: Parse Error: Identifier "Steam" not declared in the current scope.
   at: GDScript::reload (C:/Users/CQY/AppData/Local/Temp/pck_matrix_6xtkyc_g/F_addons_plus_path_env/_probe.gd:5)
```

命中的是 `C:/Users/CQY/...` —— 完整 Windows 用户目录。

## 二、范围界定（重要）

| 来源 | 是否含 PII | 说明 |
|---|---|---|
| **游戏自己的 `Logger.log()`** | ✅ **0 行** | 我们的结构化日志（`sys=... ev=...`）**完全干净**——`Logger` 从不写绝对路径 |
| **Godot 引擎的错误输出** | ⚠ **会写** | 引擎在 `Parse Error` / `Failed to load script` 等报错里带**脚本的绝对路径** |

→ **我们的 PII 契约（`logger.gd` 头注释：禁止输出 `globalize_path()` 结果、绝对路径）没有破。**
→ 泄漏源是引擎，不是 `Logger`。

## 三、为什么现在才暴露

**只在脚本加载失败时才会写**。正常运行的工程不会有 Parse Error，所以平时看不出来。
本轮是因为跑 PCK 加载矩阵、故意让 `Steam` 符号不存在（`Identifier "Steam" not declared`）
才触发的。

**风险场景**：
1. 玩家装的机器上某个脚本解析失败（资源损坏 / 版本不匹配）→ 引擎把**玩家本机的绝对路径**
   （含 Windows 用户名）写进 `%APPDATA%\SafeHouse\logs\`
2. 这些日志**会随存档/崩溃报告一起发给客服**（架构里提到"客服省事"）
3. → 违反 S10「日志零 PII」与架构 §6.3 的 PII 契约

## 四、需要拍板的三选一

| 方案 | 说明 | 谁做 |
|---|---|---|
| A. **接受**（写进 PII 契约的例外条款） | 明确「引擎自身错误输出不在我们可控范围」；QA 判据相应调整（只扫 `sys=` 开头的行） | 架构 + QA |
| B. **发布前把日志目录清空** | 打包/CI 里加一步：导出前清 `user://logs/`；或给日志目录加「不上传」约定 | 包 E / 构建侧 |
| C. **把引擎输出也过滤** | 需要 hook 引擎的 stdout 落盘——Godot 4.3 无官方 API，可能要改引擎或用 `OS.set_stderr_enabled` 之类 | 成本高，**不推荐** |

**战斗组倾向 A + B 组合**：A 承认事实并把 QA 判据口径对齐（否则门禁会偶发红），
B 在发布流程里清一次日志目录（成本极低，收益明确）。

## 五、战斗组这边的处置（已做）

- 发现的那个污染日志文件**已清除**（是本轮矩阵测试产生的）。
- `pii_probe` 现状：**27/27 全绿**（扫存档 + 扫日志目录，5 类 PII）。
- 战斗组**不改** `logger.gd`（core 层，不属包 C）——它本来就没有 PII 问题。

## 六、给 QA 的一个具体建议

`pii_probe` 目前扫日志时**按内容匹配**（找 `C:\Users\`、`\AppData\` 等）。
如果采纳方案 A，建议把判据改成**只扫游戏自己的结构化行**（`sys=` 开头），
另加一条**独立断言**记录"引擎错误行里出现了绝对路径"作为**已知例外**，
而不是让它把整条判据判红——否则门禁会在任何脚本报错的机器上偶发红。

> 这条建议本身也是从实战里学到的：**判据要能区分"我们的问题"和"别人的问题"**，
> 否则它会变成噪音，而噪音的判据迟早被关掉——关掉之后它防的事就没人防了。
