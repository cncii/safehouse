## 2. 各包契约

### 包 B·模拟系统组
- **入口文件**：`src/systems/{time,vitals,map,inventory,tech_tree,loop}_system.gd` + `continuous_action.gd`
- **职责**：一切"游戏规则计算"——状态速率、日程推进、地图生成、背包容量、科技前置、循环产线。
- **可改**：上述文件的函数体 + 对应 `data/balance|tech|locations/*.json` 数值补全。
- **禁改**：`src/core/**`、`data/schema/**`、其它包文件、**一切已标注"定稿数值"的常量**（改数值 = 设计变更，需走需求方）。
- **只能调**：`State.apply/read/subscribe`、`Rng.hash_at/pick`、`GameLoop.gh_crossed`（订阅）、`ResolveOrder` 常量、`Localize.text`。**禁止**互相 `new()`、禁止直接持有对方引用（横向依赖白名单见各文件头）。
- **DoD（判据编号）**：M1/M2/M2b/M3/M3b/M4/M5/M13/M14（状态）· M9/P16（地图确定性）· P12/P13（背包）· P28/M31（科技）· P12b/M32/S7-b（循环收支闭合）。
- **关键纪律**：速率类数值一律走 `data/balance/*.json`（键名 `<域>_<量>_<单位>` 三段式），代码零魔法数；产线用 milli 定点（C26）；ContinuousAction 的 `refund_on_cancel` 恒 false。

### 包 C·事件与战斗组
- **入口文件**：`src/systems/{event_system,effect_sink,combat_system,spawn_service}.gd`
- **职责**：事件三类触发 + append-only 日志重放（C17）；战斗手感三件套（攻击/闪避/受击）；波次状态机与破防结算。
- **可改**：上述文件函数体 + `data/events/**` + `data/enemies/*.json`。
- **禁改**：EffectSink 的 4 类能力封闭集（`num/flag/time/spawn`，schema 已锁）；CombatSystem 的 5 个帧常量（在 time_system.gd，归 A 层契约）。
- **只能调**：`EffectSink.resolve()` 是改世界唯一通道（EventSystem 自己无写权限）；`SpawnService` 是 plan 的纯消费者（禁掷骰）。
- **DoD**：M10/P8/P9/P10/P17/P17b/P18/P23（事件）· R5/P11 系列/M19/M23（战斗波次）。
- **关键纪律**：波次完成三条件（batch 全处理 ∧ alive==0 ∧ pool_remaining==0）；夜战进行中不写档（SaveSystem 已拦）；破防目标走 `LoopSystem.pick_breach_target`（字典序 + hash，禁 randi）。

### 包 D·UI/UX 组
- **入口文件**：`src/ui/**`、`src/systems/{audio_system,scene_router}.gd`、`scenes/ui/**`
- **职责**：HUD（四条状态条 + 链状态面板 + 时段 + 警报）、全屏页、设置、音频、场景切换。
- **硬边界**：**UI 只读状态 + 上行 Command，禁止调用 `State.apply()`**（check_deps.py 的 D2 检查会拦）；一切玩家可见文本走 `Localize.text(KEY)`，源码零中文字面量（check_i18n.py 会拦）。
- **必交付的三块 UI（P1.5 硬审核项，设计已定稿）**：
  1. **建造/停机瞬间三行**：产出/天、需求/天、⚠缺口——知识型必败（R13'）的唯一解法；
  2. **链状态面板**：5 条链各显示 产出/库存/还能撑几天/卡在哪一环（S10-b：风险"已缓解"必须有 UI 支撑）；
  3. **库存两级预警**：任一资源 <2 天存量 黄→红（食物容错仅 0.9 天，无预警=容错归零）。
- **DoD**：M6（死亡界面 ≤2s）· M11b（出口二次确认）· P20（HUD 倒计时偏差 ≤1GH）· S5/S6/S8（分辨率/键位/语言）· 警报可听判据。

### 包 E·存档与平台组
- **入口文件**：`src/core/save_system.gd`（补完 to_save 组装）、`meta_system.gd`、`src/platform/steam_service.gd`
- **可改**：各系统的 `to_save()/from_save()` 挂接、GodotSteam 绑定、成就表。
- **禁改**：原子写流程、迁移链规则、种子校验——已按 QA R1/R17/R22 定案实现。
- **DoD**：M7/M8 系列（存档时机）· P6（写档中强杀 100 次可加载）· P7（读档 diff=0）· S9（出站 0，含 GodotSteam 失败回连验证）· S10（PII 扫描）。
- **注意**：唯一待验证项 = GodotSteam 初始化失败后是否回连 Valve（架构侧挂账 20+ 轮，防火墙 + Process Monitor 验证）。

### 包 F·数据与测试组
- **入口文件**：`data/**` 补全、`tests/**`、`tools/**`
- **职责**：把设计定稿数值落成 JSON（按 schema 格式，先落 `graph/` 边表再落数值表）；把 QA 判据表（85+ 条）逐条移植成可执行断言；跑变异测试（每条判据注明"能抓什么"，变异体须"只有目标判据变红"）。
- **产出物**：`data/UNDEFINED.md` 缺数清单（五格：被谁需要/缺什么/影响什么/谁能定/阻塞什么）。
- **DoD**：validate_data 7/7；test.ps1 四 stage 全绿；每个变异体有"捕获 + 无误伤"实测记录。

## 3. 协作纪律（三方 30+ 轮交叉审核沉淀，违反 = 返工）

1. **数值唯一来源**：改数直接编辑 `data/**/*.json`，跑 `tools/gen_values.py` 生成值表；**禁止在消息/文档里手打数值表**（副本数 ≥ 通道数 + 1，"权威值表发出 30 分钟就过期"是实测事故）。
2. **引用数值带版本**：跨团队传数格式 `值@来源版本`；接收方对"别人算好的数"必须复算（架构侧抄 QA 示例值翻车实录）。
3. **每条风险必须有证伪方式**（"什么证据能证明它不存在"），否则不许进清单；标"已缓解"必须附守护断言，否则自动降级"已接受"。
4. **术语先定义**：最低/足够/可行/余量 这类判据性词必须指向 `data/glossary.json` 的唯一定义（同形歧义已实际撞车 5 次：天/前门/耗时/最低可行 level/余量）。
5. **新增状态路径**：改 `data/schema/state_contract.json`（路径×类型×范围×writers），不改代码；writers 白名单变更 = 架构变更，需需求方+架构+QA 三方确认。
6. **门禁两段报告**：机器判定（gate）与人工审查（review）分开列，报告首页印 coverage_statement（由 test.ps1 生成，禁止手写"全部通过"）。

## 5. 团队分配建议（主理人编排，依据 §1 依赖关系）

**推荐：3 个生产团队 + 验收权留在你手里。**

| 团队 | 承包包 | 人数建议 | 核心交付 | 关键判据 |
|---|---|---|---|---|
| **逻辑组** | B（模拟系统） | 1–2 人，需熟 GDScript | 四条状态/时间/地图/背包/科技/循环 可跑实现 | M1–M14、P12、P28、S7-b |
| **战斗组** | C + E（事件战斗 + 存档平台） | 1–2 人 | 战斗手感三件套、波次、事件日志重放、Steam 接入验证 | M19、P11 系列、P6/P7、S9 |
| **表现组** | D（UI/UX） | 1–2 人，Godot 经验要求最低 | HUD、三块硬 UI（建造三行/链状态面板/库存预警）、音频、场景 | M6、M11b、P20、S5–S8 |
| **美术组** | 资产管线（R6/§7 承包） | 1–2 人 | style_contract + palette_map shader + 分批素材（见 docs/tasks/任务书_美术组_资产.md）| check_assets.py A1–A4 + 同屏对比人工验收 |
| **测试组** | F（验收与测试基建） | 1–2 人 | harness 修通 + 判据移植 + 变异测试 + 每周报告（见 docs/tasks/任务书_测试组_包F.md）| F1–F6：五 stage 全真跑 + 变异"捕获无误伤" |
| **（不外包）** | A（core 地基） | — | 已交付，只读分发给所有团队 | 门禁本身 |
| **（留验收）** | F（数据与测试） | 你自己 / 或指定一人独立 | 边表落数、判据移植、变异测试 | test.ps1 全绿 + 变异报告 |

**为什么是 3 个，不是 2 个或 4 个**：
- ❌ **2 个**（逻辑+表现）：B+C 合并后都挤在 EffectSink 这一条"改世界"通道上，单人瓶颈在联调；战斗手感（R5）需要专注迭代，混进模拟组会被排到最后。
- ❌ **4 个**：E 只有 1–2 周工作量，独立成队开不起来；且 C、E 贴同一批 core 契约（夜战不写档 / SteamService 抽象），拆开多一条协调线。
- ✅ **3 个**：按"谁贴谁共享契约"切——B 独占规则计算，C+E 共享 core 存档与平台契约，D 独立走桩。

**F 不外包给任何生产团队**：验收权不能交给生产方（"自己写测试自己过"正是 QA 纪律要防的利益冲突）。最小形态 = 你自己每周跑一次 `tools/test.ps1`。

**并发模型**：接口已冻结，三队**可以同时开工**（各用桩开发，不互相等）。真正的汇合点只有三个：
1. B 的 vitals+time 落地 → 首批 M1/M2/M3 真红
2. C 的 combat 接入 time 帧常量 → M19/P11
3. 首个灰盒（B+C 最小闭环：能走/能饿死/能存读档）→ **用户试玩闸门**（手感不达标不许进资产阶段）

**发包时每个团队给三样**：① 本文件对应小节 + 其名下 `src/systems/*.gd`（文件头即契约）② `data/` 只读副本（改数走 JSON 提交，禁发表格）③ `tools/test.ps1`（他们的 DoD 用红绿说话）。
