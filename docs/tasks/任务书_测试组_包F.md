## 4. 变异测试（QA 已定标准，照此执行）

```
每个变异体两条硬标准：
  ① 目标判据变红          （抓到了）
  ② 只有目标判据变红       （无误伤——全红说明那批判据在测同一件事）
未满足 → 标"未正确捕获"，即使它红了。

首批变异体（按影响面）：
  windup 8→7 帧 → 应红 F0-b
  文档秒值 0.1333→0.12 → 应红 C28-b
  饥饿速率 5→6/GH → 应红 M2
  GH 帧数 4320→4300 → 应红 M1/P1①
  破防候选不排序 → 应红 M30/M19 类确定性断言

产出：变异报告（哪些判据是摆设）——这比通过率值钱。
M30 金标准锚点（tests/run_tests.gd 内硬编码 4320/816480 等）不读任何源，
它的价值就在于不会自动改；改锚点必须写裁决记录（实现错 or 设计变更）。
```

## 5. 红线（测试红 ≠ 实现错，三因分流）

测试红了，先归因再动手：

| 红的原因 | 谁修 | 你们做什么 |
|---|---|---|
| **判据自己写错**（首轮常见，QA 预估 20–30%） | 测试组 | 修判据 + 记修订 |
| **实现错** | 生产组 | **报告退回**，附最小复现；不许自己顺手改 src/** |
| **基线错**（设计值有问题） | 需求方 | 上报老板，禁止自行改 balance |

外加两条铁律：
- **禁改被基线约束的设计值来让测试通过**（QA 纪律第 9 条——"测试绿了会把错固化"）。
- **"机制存在即在运行"**：标准写了没跑 = 没缓解；test.ps1 里"跳过"的 stage 一律不许计通过。

## 7. 协作纪律

- 判据引用带版本（`P1@v1.x`）——"引用旧版数"比"算错"更高频，已有实测。
- 每条判据落笔四问：适用域？随第二变量分裂？余量/误差 >3？失败可归因？
- 扫描类判据空输入 → "未生效"，不判通过（三层空跑判负）。
- 报告里"机器判定"与"人工审查"绝不合并——混写会让人以为全绿 = 12 条都过了。
