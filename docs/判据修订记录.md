# 判据修订记录（包 F · 测试组）

**纪律**：测试红了先三因分流（判据错自修 / 实现错退生产组 / 基线错上报老板）。
凡判据修订，在此登记编号、原式、错因、新式、证据——不复用上一版结构。
修订原则：期望值必须是**独立的设计锚点**，不许取被测代码自算值（防恒真式断言，本项目已实测三连坑）。

## 修订 #1 · 运行形态（2026-10-20 · 包 F）

- **对象**：`tests/run_tests.gd` 运行方式：`godot --headless -s tests/run_tests.gd`（extends SceneTree）→ **场景方式** `godot --headless res://tests/test_main.tscn`（extends Node，挂 `tests/test_main.tscn`）。
- **错因**：`-s` 主脚本编译早于 autoload 注册，凡被加载脚本引用 autoload 标识符（`State` 等）即编译失败——`vitals_system.gd` 整体挂掉 → **M2 死钟 / M2b / M3 / M3b / M4×4 共 8 条判据从未真跑过**；且 `-s` 下 `Node._ready()` 不触发，空表态断言无意义。`MIN_ASSERTS=75` 恰按截断态校准，空跑守卫对此失明。
- **归属**：harness 缺陷（包 F 修），**非实现错**——正常启动下工程零错误（实测）。
- **新式**：场景方式启动完整工程，autoload 全就位；`MIN_ASSERTS` 75 → **83**（vitals 8 条恢复计入）。
- **证据**：首跑场景方式 83 断言全执行，vitals 段 8 条恢复（M2 PASS 100±2s 死钟）。
- **影响**：`tools/test.ps1` stage 4 命令同步更换（见修订 #2 前置改动）。

## 修订 #2 · M30 combat-chain（2026-10-20 · 包 F）

- **原式**：`TimeSystem.INCAP_TICKS == 216 and TimeSystem.INCAP_TICKS % 60 == 0`
- **错因**：把「帧数 ÷ fps = 秒值」误写成「帧数能被 fps 整除」。216 % 60 = 36 ≠ 0 → **恒假**，从首跑起必红。
- **归属**：判据自己写错（实现正确：架构 1419/1518/1522 三处均写"失能 216 帧 = 3.6s"；战斗组 2026-10-20 已复核并报包 F）。
- **新式**：`TimeSystem.INCAP_TICKS == 216 and is_equal_approx(INCAP_TICKS / 60.0, 3.60)`
- **证据**：修后 PASS；F0-b 秒值链（3.60s）交叉验证一致。

## 修订 #3 · M2b / M3b 跨零单帧份额（2026-10-20 · 包 F）

- **原式**：`VitalsSystem.zero_cross_frame_share_ok(loss)`（函数内写死 `份额 ≤ 1%/60`）
- **错因**：把**饥饿侧 1.0%/s 的单帧份额**当成了通用上限。渴的设计定稿是 **1.5%/s**（架构冻结值），单帧份额 1.5/60 > 1/60 → 对渴侧**恒假**（M3b 从写下第一天起不可能绿）。M2b 边界恰好过（1.0/60 ≤ 1.0/60 + 1e-9），属侥幸绿。
- **归属**：判据自己写错（实现正确：vitals_system.gd `_tick_hp_drain` 按 milli 定点逐帧扣）。
- **新式**（M2b/M3b 改直调纯函数 + 独立设计锚点）：
  - M2b: `is_equal_approx(VitalsSystem.hp_loss_per_tick(loss_h), 1.0 / 60.0)`
  - M3b: `is_equal_approx(VitalsSystem.hp_loss_per_tick(loss_t), 1.5 / 60.0)`
- **能抓**（比原式更强）：漏除 60 / 整秒整块扣血 / 速率漂移（json 改 1.5 → 3.0 即红）/ 帧基 TICKS_PER_SEC 被改。
- **证据**：修后 M2b/M3b 双 PASS；1.5 与 1.0 与 survival.json `hp_loss_*_zero_per_sec` 一致，与 M2/M3 死钟（100s/66.7s）互洽。
- **备注**：`zero_cross_frame_share_ok()` 因此不再被判据引用，成为 src 侧待淘汰 helper——测试组不改 src，仅在此留痕，是否删除归包 B。

## 修订 #5 · M31-2 层单调判据（2026-10-20 · 包 F）

- **原式**：前置层**严格低于**本层（`>=` 记违规）
- **错因**：把 M31「tier↔前置深度」的机械义补过头。首跑红 4 处，经 Python 独立复算复核：`unlock_filter_core(L3)←unlock_water_filter(L3)`、`unlock_water_filter(L3)←unlock_rain_collector(L3)`、`unlock_sample_culture(L3)←unlock_mushroom_bed(L3)`、`unlock_rooftop(L2)←unlock_reinforce_door(L2)`——**同层链式前置是数据真实形态且玩法合理**（层=大致阶段，非严格拓扑层）。
- **归属**：判据自己写错（数据无违规；实现与数据一致）。
- **新式**：前置层**不得高于**本层（`>` 记违规）——允许同层链，禁倒挂（如 L1 引 L3 前置即红）。
- **证据**：修后 PASS；4 处同层链在允许集内。
- **待办**：M31 原文「ending→2×L3；support→1L3+1L2」的**数量配额**仍待 QA 判据表落盘后补移植（本文件头已注明，不猜、不编）。

## 修订 #6 · M30 phase-A / P1-1 结构判据（2026-10-20 · 包 F · 变异驱动）

- **触发**：变异体 V4（GH 帧数 4320→4300）实测红集 = {M1、M30 1GH、P12b×2}——**QA 预判应红的 P1① 与 phase-A 判据全部没红**。变异报告价值实证。
- **错因**：
  1. `P1-1 formula`（`FULL_RUN == 7*PHASE_A + 7*PHASE_B`）两侧都是对运行常量的引用 → **恒真式**（本项目第 4 例，期望值被被测代码自算）；
  2. `M30 phase-A`（`== 15 * 4320`）与 `P1-1 overtime`（`== 9 * 4320`）右侧是冻结字面量——GH 常量漂移时"phase-A 必须是 15 个 GH"的**倍数关系断裂**（64800 ≠ 15×4300）测不出来。
- **归属**：判据自己写错（实现常量本身自洽）。
- **新式**：phase-A → `== 15 * FRAMES_PER_GH`；overtime → `== 9 * FRAMES_PER_GH`（结构式，抓倍数关系）；formula 恒真条删除（绝对值锚点由 M30 full-run 的 816480 字面量承担，1GH==4320 锚定绝对 GH）。结构关系 + 绝对锚点互补后漂移必红。
- **证据**：修订后 V4 复跑红集扩大（见变异报告 V4），无误伤。断言总数 122 → 121。
- **教训**：判据的期望端若与被测端同源（同为引用或同为冻结字面量），要么恒真要么对连锁漂移免疫。写判据先问：**这个判据在「上游常量变了」的世界里红不红？** 不红的判据是摆设。
