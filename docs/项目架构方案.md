# 《末日：我有一座安全屋》项目架构方案 v1

> **适用对象**：个人开发者，单人，15–20 h/周，目标 Steam 上架
> **出具**：游戏研发工作室 · 范可控（制作人）汇编
> **分工**：技术部分 · 柯桥良（技术架构总监）｜玩法基线 · 游有方（创意总监）｜验收判据 · 严过关（QA）
> **日期**：2026-10-19
> **状态**：可用，但有 5 项数值缺口待补（见第 11 章）。缺口不影响目录结构与模块划分动工，但会让"验收判据"落不了地。

---

## 0. 三句话摘要

1. **引擎用 Godot 4.x + GDScript + JSON 数据层。** 理由不是"它流行"，而是这个项目真正的工作负载是**反复调参**（4 条状态 × 4 类产出 × 30 个科技节点 × 14 天日程），GDScript 无编译等待的迭代速度是唯一撑得住 18 个月长跑的选项。
2. **这个项目的技术难点不在渲染，在两件事**：① 12 个系统之间的写权限收敛；② "同一天重开，世界必须完全一致"的确定性种子。这两件事不做对，后面所有内容都是白做。
3. **不要手搓 9 个地点场景。** 1 个 `location_base.tscn` + 1 个读 JSON 的房间拼装器，9 类地点 = 3 套 tile 主题 × 参数差异。这是本方案对"内容量爆炸"这个最大死因的核心应对，能省约 100 小时。

## 1. 关键决策速览

| # | 决策项 | 结论 | 谁定的 |
|---|---|---|---|
| 1 | 引擎 | **Godot 4.x**（加权 8.50 / 10） | 柯桥良 |
| 2 | 语言 | GDScript（不混 C#，避免双语言构建链） | 柯桥良 |
| 3 | 数据层 | 外部 JSON，代码零魔法数，启动期双重校验 | 柯桥良 |
| 4 | 存档 | **JSON + gzip + 原子重命名**，两个文件（`save.sav` / `profile.sav`） | 柯桥良 |
| 5 | 渲染 | 内部固定 **640×360**，整数倍缩放，绝不小数缩放 | 柯桥良 |
| 6 | 状态写入 | **唯一入口 `StateStore.apply()`** + writers 白名单，越权写入 debug 构建直接崩 | 柯桥良 |
| 7 | 防 S/L | `splitmix64` 派生 + **位置无关 hash**，同一天重开世界完全一致 | 柯桥良 |
| 8 | 事件能力 | **封闭 4 类**：改数值 / 开关 / 压缩时间 / 生成实体。不做通用脚本引擎 | 柯桥良 |
| 9 | 战斗形态 | 近战 + 翻滚闪避为主，枪械稀少 | 游有方 |
| 10 | 第 8 天后玩法 | **白天基建流水线 + 夜晚守门**（不是看进度条） | 游有方 |
| 11 | 一局结构 | 7 天搜刮 + 7 夜守家。**「4.5–5.5 h」只适用于无死亡通关**；含重开不计上界，只看中位数（目标 5.5–7.5 h，1–2 次死亡） | 游有方 + 范可控裁定 |
| 12 | 进度闸门 | 三档 82 条判据，全自动 72 / 半自动 4 / 人工 6（2 条 not_covered） | 严过关 |

## 2. 引擎与技术栈选型

### 2.1 加权对比

权重按"单人 + 数据驱动模拟 + Steam 上架"这一具体场景定，不是通用评分。

| 维度 | 权重 | Godot 4.x | Unity 6 | GameMaker | Electron+TS |
|---|---|---|---|---|---|
| 2D 像素工作流 | 15% | 9 | 7 | 10 | 6 |
| 数据驱动系统能力 | 15% | 8 | 9 | 5 | 7 |
| **单人体量下的开发效率** | **20%** | **9** | 6 | 8 | 3 |
| 存档与版本迁移 | 10% | 8 | 7 | 5 | 8 |
| Steam 集成成本 | 10% | 6 | 9 | 7 | 3 |
| 授权与分成 | 10% | 10 | 4 | 6 | 10 |
| 长期可维护性 | 10% | 9 | 6 | 5 | 7 |
| 学习曲线 | 5% | 8 | 6 | 8 | 7 |
| 素材包兼容 | 5% | 9 | 10 | 6 | 5 |
| **加权总分** | 100% | **8.50** | **7.00** | **6.85** | **5.95** |

### 2.2 三条否决理由

**否决 Unity 6**
- 单人体量开发效率 6 分是硬伤：C# 编译 + 重型 Editor 启动，一次"改一个数字看效果"的循环比 GDScript 慢 3–5 倍。这个项目要反复调 4 条状态、4 类产出、30 个节点、14 天日程——**调参频次就是核心工作负载**，引擎的迭代延迟被直接放大。
- 授权与分成 4 分：2023 年 Runtime Fee 事件证明它的许可条款会中途变。跨 2 年的项目不能把"上架时还免费吗"交给外部决策。
- 2D 像素工作流 7 分：能做，但 Pixel Perfect Camera、Sprite Atlas、导入管线处处要手动掰，是持续摩擦成本。

**否决 GameMaker**
- 数据驱动能力 5 分且无上升空间：GML 没有真类型系统与模块边界，30 节点科技树 + 条件事件表 + 波次状态机会退化成一堆全局变量和 `switch`。这个游戏 70% 的代码是"读表 → 算 → 写状态"，恰好不是 GameMaker 的长处。
- 存档迁移 5 分：没有序列化基础设施，schema 演进全靠手搓，第 5 次改结构时必然出隐性损坏。

**否决 Electron + TS 自研**
- 开发效率 3 分：要自己实现 tilemap、碰撞、动画状态机、音频总线、手柄输入。这不是选引擎，是"先花 6 个月写引擎再开始做游戏"。
- Steam 集成 3 分：`greenworks` 已停更多年，Steamworks 原生绑定要自己编 node-gyp 多版本产物，Overlay 在 Electron 里长期有问题。这是最不该让单人开发者碰的坑。

### 2.3 主动放弃的东西（是决策，不是遗漏）

| 放弃项 | 原因 |
|---|---|
| ❌ 3D / 骨骼动画 / 动捕 | 与"像素精灵 + 立绘"路线冲突 |
| ❌ 联网 / 账号 / 云存档 / 埋点 / 内购 / 反作弊 | 用户硬约束；约 30% 工作量直接消失 |
| ❌ 自定义关卡编辑器 / 对话编辑器 | 编辑器本身就是一个项目。地点用 JSON 参数化 + 场景模板，前期多写 200 行解析，省掉 1 个月工具开发 |
| ❌ 通用事件脚本引擎（DSL / 表达式求值） | 见 4.5 节，事件只允许 4 类能力；代价是编写略笨，收益是永不出现"事件脚本引发的诡异 bug" |
| ❌ macOS / Linux 首发 | 认证与测试成本对单人不成比例；只保留"不留死路"的编码纪律 |
| ❌ 对象池 / ECS / 多线程资源加载 | 40 个实体的规模用不上 |

### 3.2 各目录的红线

| 目录 | 放什么 | **不许放什么** |
|---|---|---|
| `data/` | 一切可调数值、文本键、事件定义、地点图、掉落表 | 任何 `.gd`；任何 `.tscn`；任何绝对路径 |
| `data/locale/` | 只有 CSV | 不许有硬编码中文的 `.json`（事件文本写 `"text_key": "EV_X_DESC"`） |
| `src/core/` | 基础设施：状态、存档、随机、日志、性能 | **不许出现任何游戏规则**（"饥饿 5/GH"只能来自 data） |
| `src/systems/` | 业务规则，只通过 StateStore 写状态 | 不许直接持有 `GameState` 引用；不许 `new()` 另一个系统（用注入） |
| `src/ui/` | 渲染 + 输入 → Command | **不许调用 `StateStore.apply()`**；不许消费 RNG |
| `src/actors/` | 场景内运行时实体 | 不许把这些实体的字段写进存档（只有游标/进度入档） |
| `addons/` | 第三方插件原样 | 不许改内部代码（要改就 fork 到 `src/platform/`） |
| `assets/` | 原始美术音频 | 不许放 `.gd`/`.tscn`；不许放未过 `style_contract.md` 的素材 |
| `scenes/debug/` | 压力测试、调参场景 | 不许被 release 导出引用 |
| `build/` | 产物 | 不许进 git；不许手改 |

**数据与代码分离的落点**：代码里不允许出现 `if enemy_hp == 100`，只能 `Balance.getf("survival.hunger_rate_per_gh")`。CI 加一条 grep：`src/systems/` 出现 3 位以上数字字面量即警告。

## 4. 核心模块划分

### 4.1 十二模块总表

| # | 模块 | 一句话职责 | 对应数据 | 明确不做 |
|---|---|---|---|---|
| 1 | **StateStore** | 唯一状态写入口 + 写入鉴权 | `schema/state_contract.json` | 不做任何规则计算；不理解"饥饿"是什么 |
| 2 | **TimeSystem** | GH 时间基准 / 时段 / 阶段 / 跳夜 | `balance/time.json` | 不判断"玩家该不该睡"；不知道事件存在 |
| 3 | **MapSystem** | 节点图 / 布局生成 / 搜刮标记 / 回填 | `locations/*` | 不加载场景；不管背包；不推进时间 |
| 4 | **InventorySystem** | 物品增删 / 耐久 / 容量 / 自动配给 | `items/*` | 不直接改 player 字段（发 ChangeSet） |
| 5 | **TechTreeSystem** | 解锁 / 研究中 / 图纸 | `tech/*` | 不实现节点效果（交给 effect_sink） |
| 6 | **LoopSystem** | 4 类产出累积 / 库存上限 / 3 个维护动作 | `balance/loop.json` | 不自动投喂玩家；不碰 `player.*` |
| 7 | **EventSystem** | 3 类触发 + 4 类能力 | `events/*` | **零写权限**，只产出 Effect |
| 8 | **CombatSystem** | 攻击/闪避/伤害/波次 | `balance/combat.json`、`waves.json` | 实体不入存档 |
| 9 | **SaveSystem** | 序列化 / 迁移 / 原子写 / 种子校验 | `schema/save.schema.json` | 不做 UI 层多档位（接口不存在） |
| 10 | **UISystem** | 只读绑定 + Command 上行 | `locale/strings.csv` | **完全禁止写状态、禁止消费 RNG** |
| 11 | **AudioSystem** | SFX/BGM/警报 ducking | `assets/audio/` | 纯消费者，不回写任何东西 |
| 12 | **SceneRouter** | 场景加载/切换/暂停模拟 | `scenes/*` | 不驱动时间 |

### 4.2 关键接口

**StateStore（状态管理）**

```gdscript
func apply(cs: ChangeSet) -> ApplyResult        # 唯一写入口，带鉴权
func read(path: String) -> Variant              # 只读取值，返回副本
func snapshot() -> ReadOnlyState                # 不可变快照（存档用）
func subscribe(prefix: String, cb: Callable) -> int
func reset_for_new_game(seed: int, difficulty: String, cycle: int) -> void

class ChangeSet:
    var source: String          # "loop_system" / "event:ev_neighbor_water" / "ui:hud"
    var reason: String
    var ops: Array[Op]          # Op{path, verb:ADD|SET|CLAMP|TOGGLE, value}
```

`apply()` 先查契约表，若 `source` 不在该 path 的 `writers` 白名单 → 拒绝。**debug 构建直接 assert 崩溃**，release 记日志丢弃。这是"禁止各处直接改字段"的机械保障。

```jsonc
// data/schema/state_contract.json 片段
{
  "player.hunger": {"type":"float","min":0,"max":100,
                    "writers":["loop_system","inventory_system","effect_sink"]},
  "time.gh_elapsed_today": {"type":"float","min":0,"max":24,
                            "writers":["time_system"]}      // ← 只有时间系统能推时间
}
```

**TimeSystem（时间与日程）**

```gdscript
enum Phase { PREP, OUTING, EVENING, NIGHT_WAVE }
enum Stage { A_LOOT, B_SIEGE }
enum TimeMode { REALTIME, SKIP, WAVE_DRIVEN }

func tick(delta_real_sec: float) -> void     # 由 GameLoop 每帧唯一调用
func request_skip_to(target: Phase) -> SkipResult   # 跳夜（仅阶段 A 有床）
func is_curfew() -> bool                     # 18:00 后
func is_lockdown() -> bool                   # 20:00 后门锁死
```

**夜间波次不能用真实时间驱动 GH**，否则玩家躲角落不打，天亮了自己就赢了：

| 模式 | GH 推进公式 | 用在哪 |
|---|---|---|
| `REALTIME` | `gh += delta_sec / 72.0` | 阶段 A 全天、阶段 B 白天经营 |
| `SKIP` | `gh += delta_sec / 47.4`（≈1.52×，24GH 压到 ~19min） | 阶段 A 跳夜 |
| `WAVE_DRIVEN` | `gh = 18.0 + 12.0 × kills_ratio`（不跟真实时间） | 阶段 B 夜间、阶段 A 被敲门 |

阶段 A 的"被敲门 → 中断睡眠转即时应战"就是 `REALTIME → WAVE_DRIVEN` 的一次模式切换，复用同一套波次驱动。

**EventSystem（事件系统）—— 封闭 4 类能力**

```gdscript
class Effect:
    var kind: String    # 只能是 "num" | "flag" | "time" | "spawn"
    # num   : path, verb(ADD/SET/CLAMP), value     → 改数值
    # flag  : scope, id, field, value(bool)         → 开关
    # time  : target(SHIFT_END/ADD_GH/FORCE_SLEEP), value → 压缩时间
    # spawn : table_id, count, anchor               → 生成实体（只能引用 spawn_tables.json 的 id）
```

`effect.schema.json` 用 `additionalProperties: false`；出现未知 `kind`、或任何 `script`/`expr`/`call`/`on_fire` 字段 → **启动即失败并打印文件名**，不是运行时悄悄忽略。

**RngService（确定性随机）**

```gdscript
static func mix64(x: int) -> int                 # splitmix64，自己实现，不依赖引擎 RNG
func day_seed(day: int) -> int                   # mix64(global_seed ^ (day * GOLDEN))
func stream(purpose: StringName, day: int) -> RandomNumberGenerator
func hash_at(purpose: StringName, day: int, keys: PackedStringArray) -> int  # 位置无关
```

### 4.3 依赖分层与写权限

```
┌── L4 表现层（只读，禁止写状态）──────────────────────┐
│  UISystem      AudioSystem      SceneRouter/Actor    │
│      │ Command（唯一上行）  ▲ 订阅通知                │
└──────┼───────────────────────────────────────────────┘
       ▼
┌── L3 系统层（规则，只能经 ChangeSet 写）─────────────┐
│ Time│Map│Inventory│Tech│Loop│Event│Combat│Save        │
└──────┬────────────────────────────────────────────────┘
       ▼ ChangeSet(source, reason, ops)
┌── L2 状态层 ─────────────────────────────────────────┐
│ StateStore.apply()  ← 唯一写入口                     │
│ StateContract       ← 路径 × 类型 × 范围 × writers    │
└──────┬────────────────────────────────────────────────┘
       ▼
┌── L1 基础层（无游戏规则）────────────────────────────┐
│ RngService│Logger│Localizer│PerfGovernor│GameLoop     │
└──────┬────────────────────────────────────────────────┘
       ▼
┌── L0 数据层（纯 JSON，运行期只读）───────────────────┐
│ data/**  启动时加载 → 不可变 Table                    │
└───────────────────────────────────────────────────────┘
```

| 模块 | 状态读 | 状态写 |
|---|---|---|
| StateStore | ✓ | ✓（唯一写者） |
| TimeSystem | ✓ | 仅 `time.*` |
| MapSystem | ✓ | 仅 `map.*` |
| InventorySystem | ✓ | `inventory.*`、`player.hunger/thirst/hp`（消耗品效果） |
| TechTreeSystem | ✓ | 仅 `tech.*` |
| LoopSystem | ✓ | 仅 `facilities.*`、`loop.*` |
| **EventSystem** | ✓ | **零**（只产 Effect） |
| EffectSink | ✓ | 按 kind 落地，白名单专列 `effect_sink` |
| CombatSystem | ✓ | `player.hp/stamina`、`combat.*` |
| SaveSystem | ✓ | 仅新局时整体替换 |
| **UI / Audio / SceneRouter / Actors** | ✓ | **完全禁止** |

**允许的横向依赖（白名单，其它一律违例）**

| 谁 → 谁 | 方式 |
|---|---|
| EventSystem → EffectSink → {State, Time, SpawnService} | 单向调用 |
| TechTreeSystem → EffectSink | 单向调用（科技效果复用同一套能力集） |
| LoopSystem → TechTreeSystem | **只读** `is_unlocked()` |
| CombatSystem → InventorySystem | **只读** `equipped()` |
| CombatSystem → TimeSystem | **只读** `is_lockdown()` |
| MapSystem → RngService | 取命名子流 |
| InventorySystem → LoopSystem | **只读** `store_of()` |

**反向禁例（CI 检查项）**：`TimeSystem` 不许 import `EventSystem`；`InventorySystem` 不许 import `MapSystem`；`src/ui/**` 不许 import 任何带 `apply` 的东西；`addons/**` 不许被 `src/core/**` import。

### 4.4 单向数据流

```
   玩家输入 → UI/Actor ──Command──► GameLoop ──分发──► System
                                                        │
                                              ChangeSet(source, ops)
                                                        ▼
                                          StateStore.apply() ──鉴权──► GameState
                                                        │
                                              notify(prefix, delta)
                                        ┌───────────────┴───────────────┐
                                        ▼                               ▼
                                  UI 更新显示                     Audio 播放反馈
```

**一句话**：`GameState` 只能被"下降的 ChangeSet"改，改完只能被"上升的通知"观察。任何读→写直达路径（UI 里 `player.hp -= 10`）都是违例，靠 writers 白名单在运行期挡住。

## 5. 存档系统设计

### 5.1 格式结论：JSON（UTF-8）→ gzip → 原子重命名

| 方案 | 判定 | 理由 |
|---|---|---|
| 引擎原生二进制 | ❌ | 引擎升级后二进制布局可能变，2 年项目必然撞上；坏了无法抢救 |
| 自研二进制 | ❌ | 单人没有维护一套二进制格式的带宽 |
| **JSON + gzip** | ✅ | 可读可 diff 可手改（调试救命）；迁移就是字典操作；300KB 压到 30KB 级；这个数据量根本不构成性能问题 |

### 5.2 两个文件，不是一个

| 文件 | 存什么 | 为什么分开 |
|---|---|---|
| `user://save.sav` | 单局状态（玩家/背包/科技/设施/地图/时间/事件/种子） | 死亡/新局要整体重置 |
| `user://profile.sav` | 周目数/难度/多周目解锁/统计/立绘 | **必须跨局存活**。塞进 save.sav 会被新局清掉；放内存退出即丢 |

### 5.4 版本迁移（无例外）

1. **只增加**字段或改结构，**不改**已存在字段的语义。要改语义 = 加新字段 + 老字段标 `deprecated` 一个版本后再删。
2. 每次 bump `SCHEMA_VERSION` 必须同时提交：① 一条 `_migrate_vN_to_vN+1`（只允许 N→N+1，禁止跳跃）；② 一份 `tests/fixtures/save_vN.json` 历史快照。测试遍历全部 fixture 跑完整迁移链。
3. 版本号**永不重用**。回滚发布也不回退版本号。
4. 迁移前先把原档复制为 `save.sav.premigrate`。
5. 读到比当前更新的版本 → 拒绝并说明，**不尝试兼容**。

### 5.5 原子写入

```
1) 写 save.sav.tmp
2) 回读校验：能解压且能 parse 才算写成功 —— 失败则保留旧档，不覆盖
3) 旧档降级为 save.sav.bak
4) 同分区 rename（原子替换）
```

**诚实说明**：Godot 的 `FileAccess` 没有暴露 `fsync`，无法承诺"断电瞬间最后一次写入一定落盘"。这套方案保证的是 **"要么完整旧档，要么完整新档，永不出现半截文件"**。要更强保证得写 GDExtension 调 Win32 `FlushFileBuffers`，不值得。

**加载兜底**：`save.sav` → `save.sav.bak`（提示"主档损坏，已从备份恢复"）→ `save.sav.premigrate` → 都没有则回主菜单并明确告知，**绝不静默开新局**。

### 5.6 局种子 + 天数派生（防 S/L 的唯一手段）

```gdscript
func day_seed(day:int) -> int: return mix64(global_seed() ^ (day * GOLDEN))
func hash_at(purpose, day, keys) -> int:     # 位置无关：不消耗流，直接由键算值
    var h := day_seed(day) ^ RNG_SALTS[purpose]
    for k in keys: h = mix64(h ^ str_hash(k))
    return h
```

| 子流 | 谁消费 | 方式 |
|---|---|---|
| `LOOT` | MapSystem | `hash_at(LOOT, day, [loc_id, loot_point_id])` — 只搜一半死掉，重开搜同一半结果一致 |
| `SPAWN_WAVE` | CombatSystem | `hash_at(WAVE, day, [night_index, batch, slot])` — 不依赖击杀顺序 |
| `SPAWN_AMBIENT` | SpawnService | **`hash_at(..., [loc_id, slot])`，按槽位直接算**（v1.2 修订：原设计用顺序流消费，会随开箱顺序漂移 → 破坏同日一致）|
| `EVENT_ROLL` | EventSystem | `hash_at(..., [slot_index])` — 每时段独立掷骰 |
| `EVENT_PARAM` | EventSystem | `hash_at(..., [event_id])` |
| `REFILL` | MapSystem | `hash_at(..., [loc_id])` |
| `FLAVOR` | UI | 纯文案抖动，不参与玩法 |

**七条不可协商的契约**

1. **只有 `RngService` 能创建 `RandomNumberGenerator`**。别处出现 `randi()`/`randf()`/`randomize()`/`RandomNumberGenerator.new()` → CI `exit 1`。
2. 派生只依赖 `(global_seed, day, purpose_salt, 键)`，绝不依赖已消耗抽取次数、真实时间、帧率、玩家操作。
3. 消费位置唯一：`SPAWN_AMBIENT` 只在 `enter_node()` 整段预生成；`LOOT` 是纯 hash。
4. UI / Audio / Actor / `_process` 内禁止取任何 RNG。
5. 读档强校验 `day_index_of_seed == time.day` 且 `day_seed` 重算匹配，不匹配判坏档。
6. `rng_salts.json` 发布后不能改值。改 salt = 所有老存档世界重生。新增子流只在末尾追加。
7. 每日 05:00 存档点之后当天 `day_seed` 锁定 → **重试只能练技术，不能刷随机**。

## 7. 性能预算

### 7.1 分辨率：内部固定 640×360

选它的理由：16:9 常见显示器都能整数倍覆盖 —— 720p=2×、1080p=3×、1440p=4×、4K=6×、1366×768 也能 2×（1280×720 居中 + 黑边）。

三条无例外的规则：
1. 渲染只用 `CanvasLayer` + `SubViewport(640×360)`，整数倍 blit 到窗口。**绝不小数缩放**。
2. 16px 图块，摄像机对齐像素网格（`floor(pos)`），禁用平滑相机。
3. 非整数倍窗口 → letterbox 黑边，不拉伸。设置页给"整数缩放（默认）/填满屏幕（会抖动）"两选项。

### 7.2 预算表

| # | 指标 | 目标 | 超阈处置 |
|---|---|---|---|
| 1 | 内部分辨率 | 固定 640×360，整数倍 | **[门禁]** 写死在 `project.godot`，改需架构审批 |

> 标 [门禁] 的 5 条（分辨率/DrawCall/内存/启动时长/包体）没有运行时降级，因为它们是**输入常量或资源组织属性**，运行期不存在可降级的对象——为它们硬造降级动作才是过度工程。

### 7.3 现在必须做对 vs 现在绝对不做

**开工第一天就要做对（返工成本随内容量线性上升）**
1. 640×360 + 整数缩放的 `SubViewport` 管线 —— 后改等于重做所有 UI 布局
2. 图集与导入规则（统一 import preset，大图禁 > 2048）—— 后改等于重导全部美术
3. `autoload` 只放 StateStore / RngService / SaveSystem / Localization 四个轻量的，数据表懒加载
4. `PerfGovernor` 的**框架**（哪怕全空实现）—— 要有一个能计数和切档的地方

**现在绝对不要做（写进 `docs/icebox.md`）**：对象池、敌人寻路优化、GDScript 微优化、多线程资源加载、LOD/剔除。

**优化的唯一判断线**：当且仅当 ① 压力场 1% low < 50fps；② 某场景实体数达预算 60%（敌人>24 或粒子>240）；③ 发版门禁项不达标。其它一切"感觉有点慢"→ 记 `docs/perf_notes.md`，**不改代码**。

## 8. 风险清单（按"会直接导致项目做不完"排序）

### R1 · 内容量爆炸 —— 最大死因
**形态**：9 类地点 × 1–3 屏手工场景；30 节点 × 美术图标+文案+效果；15+ 事件；7 夜波次。粗算 **350 小时纯内容**，按 18h/周 ≈ **20 周只做内容**，不含调试与平衡。
**触发信号**：单个地点灰盒制作 > 8h；或开工第 3 个月还没跑通"完整一天"。
**缓解**：
1. **地点参数化，不手搓**。1 个 `location_base.tscn` + 房间拼装器（读 `themes/*.json` 的房间数/尺寸/拓扑/主题 tile）。9 类地点 = 3 套 tile 主题 × 参数差异。新增地点 ≈ 改 20 行 JSON。
2. 科技节点必须能一句话说清"它改了哪个数字/哪个 flag"。说不清的砍掉（30 个里估计有 6–8 个是"听起来酷但没机制意义"）。
3. 路线图硬锁：MVP 地点数锁 1，"可玩"锁 4，第 5–9 个只在"可上架"阶段做，且必须用第 1 条方式做。

### R2 · 平衡调参黑洞（最贵的一项）
**形态**：4 状态 × 4 产出 × 30 节点乘数 × 14 天 × 7 夜波次。人肉玩一局验证 = 5h，**一周只能验证 3 个假设**。
**缓解**：
1. **架构必须提供"无渲染数值快进"**：`scenes/debug/sim.tscn` 的 `debug_simulate_days(14, cfg)`，纯数值推演，10 秒输出一张表（每天结束的 HP/饥/渴/水/食物/电力/科技进度/是否饿死）。**必须在"可玩"里程碑之前做完，优先级高于任何内容。**
2. 所有速率只来自 `data/balance/*.json`，代码零魔法数。
3. 硬规矩：**每次只调一个文件里的一个数**，其余 freeze。一次调三个数 = 无法归因。

### R3 · 存档/种子不一致（最隐蔽）
**触发信号**：同种子同日重开两次货架不同；读档后数值微漂（hunger 差 0.3）；玩家报告"重开能刷好货"。
**缓解**：`test_determinism.gd` 字节级断言进 CI；CI grep 禁 `randi(` 等；读档强校验种子；**所有状态推进必须在整 GH 边界结算，不许按帧累加浮点**（帧率不同会导致漂移）。

### R4 · 12 个系统耦合失控
**触发信号**：修一个 bug 改了 3 个以上系统；出现 A↔B 双向调用；`player.hp` 在 6 个文件里被赋值。
**缓解**：writers 白名单 + debug 构建 assert；`check_deps.py` 扫 import 图违例 exit 1（**单人项目里唯一能替代 code review 的东西**）；每加一个系统先写它的"不做"清单。

### R5 · 战斗手感不达标
**形态**：闪避手感依赖 4 个数的精确配合（无敌帧 0.15s / 前摇 0.12s / 后摇 0.10s / 受击硬直 0.20s）。错一个就"能玩但不想再玩"，玩家不会说原因，只会退款。
**缓解**：`combat_arena.tscn` 3 秒重开、实时改那 4 个数（热重载）、显示无敌帧可视化。**铺任何内容之前先把这个调到舒服**。
**量化验收**：连续 10 场战斗里主动闪避次数 > 挥砍次数 × 0.6，且没有一场是"站着不动打完的"。

### R6 · 美术风格拼贴感
**缓解**：先写 `docs/style_contract.md` 当准入门槛（16px 网格、≤32 色、左上光源、1px 深色描边、3/4 顶视），不合规的**买了也不用**；加 `palette_map.gdshader` 把不同来源色板映射到统一 target palette（一个 shader 顶 40 小时重绘）。

### R7 · Steam 接入遗留到最后
**缓解**：**在"可玩"里程碑结束的那个周末，花 1 天做一次"最小可上传包"** —— 能启动退出、Overlay 能呼出、成就至少触发 1 个、`steamcmd` 能传到私有 build。管线打通一次，之后每次发版只是重跑脚本。不要留到"可上架"再碰。

### R8 · 单人长周期动力衰减 / 范围蔓延
**缓解**：`docs/icebox.md` 是唯一合法的新想法去处；每个里程碑必须产出"能发给朋友玩的包"；里程碑粒度不超过 6 周。

### R9 · 本地化返工
**缓解**：第一天起 `strings.csv` + `tr()`；`check_i18n.py` 扫 `src/**/*.gd` 与 `data/**/*.json` 里的 CJK → exit 1。第一天开成本 0，第 300 天开成本是重写所有 UI。

### R10 · macOS/Linux 留口（不是风险，是主动放弃）
只保留四条编码纪律（全 `user://`、不调 Win32、假设大小写敏感、NullSteam 降级），成本接近 0。不做公证、不做 Deck 认证、不做 Linux 打包测试——每个都是 20+ 小时的独立工作流。

## 9. 玩法与系统基线（架构的输入，摘要）

### 9.1 时间尺度（两个词，不许混用）

> **名义 GH**：游戏内时间轴，用于状态衰减、日程、科技研究。**不换算成现实秒。**
> **clock GH**：由真实时间驱动的时段（阶段 A 全天、阶段 B 白天经营），**1 GH = 72 s**。
> **现实时长 = clock GH × 72 s + 压缩时段的实际演出时长。**
> 两处压缩：① 阶段 A 睡眠 ② 阶段 B 夜间波次（由击杀比驱动，不跟真实时间）。

**一局纯玩法 4.51–4.75 h**（无死亡通关口径）；墙钟体感 5.5–6.2 h（含重开与加载）。需求里的「3–8 h」按墙钟口径成立。

> ⚠ 早期 QA 算出 5.44 h / 5.64 h 是**错的口径**——把阶段 B 的 77 名义 GH 当成 72 s/GH 的现实分钟，等于要求"杀得快也要坐满 12 分钟"，会把 `WAVE_DRIVEN` 这个正确设计推翻。该数字已作废。

### 9.2 阶段结构

**阶段 A · 搜刮期（D1–D7）**，一天三段：

| 段 | 游戏内 | 现实 | 玩家做什么 |
|---|---|---|---|
| 晨间准备 | 05:00–08:00（3 GH） | 3–4 min | 吃喝、点科技、整理背包、选今天去哪 |
| 白天出门 | 08:00–18:00（10 GH） | 10–12 min | 去**一个**地点：路上耗 GH + 搜刮 + 战斗 + 返回 |
| 傍晚/夜间 | 18:00–05:00（11 GH） | 3–5 min | 维修、循环系统投料、研发；或睡觉跳夜 |

门禁：18:00 后仍在外遭遇率逐 GH 上升；**20:00 后门锁死（语义 = 挡「进入」，回不了屋）** → 强制野睡（-15% HP）+ 夜间袭击判定，大概率本局结束。
> ⚠ **两个"锁"方向相反，技术上不能共用一个布尔**：阶段 A 的锁是**挡进入**，阶段 B 的锁是**挡离开**。必须拆成 `lock_entry` / `lock_exit` 两个独立语义（详见 11.6 待裁定项）。阶段 A 可跳夜（有床跳次日 05:00），代价是循环系统仍需提前投料，D4 起夜间有概率被敲门、睡眠中断转即时应战。一天只能去一个地点。

**阶段 B · 守屋期（7 个夜晚，跨 8 个日历日）**

> **修订（v1.1）**：不是"D8–D14 共 7 个日历日"——7 夜必然跨 8 个日历日。**切换点唯一：D7 20:00 门锁死的那一刻**（此时 D7 白天已结束、补给窗口已关闭、玩家必在屋内，是唯一的稳定切换点）。
> D7 20:00 → D8 06:00 是**过渡夜**：不计夜次、无波次、只播氛围音。**夜次 1 = D8 18:00**。

| 段 | 时间 | 现实 | 玩家做什么 |
|---|---|---|---|
| 白天经营 | 08:00–18:00（10 GH） | 8–10 min | 加燃料、清滤芯、补料、造陷阱路障、修门修墙、点科技、备饭备水 |
| 夜间波次 | 18:00–06:00（压缩为波次场景） | 6–8 min | 打一整波，分 2–3 小批从 1–2 入口进，撑到天亮 |

- 推进按**夜次**而非天数熬；强度递增且受白天经营成果影响（陷阱数/门耐久/电力）
- **不可跳夜**（这是核心动词）
- **夜 7 天亮 = 通关**。完成"反转链"（信号塔/血清）进结局 A/B；未完成则夜 7 强度 +30%，硬撑过算"惨胜"通关
- 有硬终点，**不做无尽模式**

### 9.3 四条状态量级

| 状态 | 上限 | 消耗 | 恢复 | 满到 0 | 归零后果 |
|---|---|---|---|---|---|
| 生命 | 100 | 受伤、饥渴归零、野睡 | 无自然回复；睡眠 +10~15；医疗包 +30~40 | — | 死亡 |
| 体力 | 100 | 冲刺 1.5/s；挥砍 3/次；翻滚 6/次；受击 -5 | 能量棒 +25、正餐 +40、床上睡 1GH +15 | — | **5% 强制睡** |
| 饥饿 | 100 | 5 /GH | 食物 1 单位 +25 | 20 GH ≈ 24 min | 每秒 -1% HP（100 秒死） |
| 口渴 | 100 | 7 /GH | 净水 1 单位 +30 | 14.3 GH ≈ 17 min | 每秒 -1.5% HP（67 秒死） |

**设计意图**：渴比饿快 40% → **渴是"该回家了"的钟**。一次 10GH 出门耗饥饿 50、口渴 70；整夜睡 8GH 掉饥饿 40、口渴 56 → 睡前必须备粮备水。归零后 67–100 秒就死 → 状态条是**硬计时器**，UI 在剩余 25% 必须给可听见警报。

### 9.4 科技树与循环系统的耦合（最关键的一张表）

**科技树（定稿 24 节点）**：L1 求生 5 / L2 基建 7 / L3 循环 8 / L4 反转 4。
材料三类：零件（通用）、电子元件（稀有）、生物样本（从丧尸尸体获取）→ **不打架点不动 L3**。

> **v1.5 修订：31 → 24 节点，砍掉 7 个。** 理由比清单重要——
> 背包扩容 I（并入储物升级）/ 绊索陷阱（与尖刺重叠，不做第二套陷阱）/ 燃烧瓶（投掷远程与"近战为主"定调冲突）/ 保温层（纯数值，玩家感知不到）/ 空气循环（要开新事件域，MVP 不划算）/ 净水大改（并入净水器三级升级）/ 隔音加固（要改波次生成逻辑且与防守价值重叠）。
> **新增 L2-9 拆解台**：解"阶段 B 全锁 → 材料只减不增"的断链（屋内 24 件家具可拆，`2 GH → 零件 ×3`，累计补约 72 零件），同时给阶段 B 添第四个动词（拆解 vs 修门 vs 研发 vs 造陷阱，抢同一个白天窗口）。

| 科技节点 | 解锁产出 | 初建 → 满级 | 覆盖每日需求 |
|---|---|---|---|
| L3-1 雨水收集器 | 脏水 | 0.20 → 0.35 /GH | 原料 |
| L3-2 净水器 | 脏水→净水（80%） | 净水 0.15 → 0.24 /GH | **64% → 103%** |
| L3-3 菌菇栽培架 | 食物 | 0.12 → 0.22 单位/GH | **60% → 110%** |
| L2-4 发电机+电力扩容 | 供电 | — | 断电时全 L3 产出 ×50%、夜间陷阱失效 |
| L3-8 医疗台 | 医疗包 | 0.4 → 1.0 /天 | — |
| L3-9 样本培养槽 | 培养样本 | 0.5 /天 | 切断"必须出门取样" |

需求对照：饥饿 120/天 ÷ 25 = **4.8 单位/天**；渴 168/天 ÷ 30 = **5.6 单位/天**。初建产 ≈ 60–64%，缺口由库存填——这就是"慢性缺血"窗口：D8–D9 靠囤货安全，D10–D11 必须升到二级。

**循环系统**：产净水/食物/电力/医疗 4 类，按 GH 连续累积（非日结算），每类独立库存上限（水 15/食 12/样本 10，储物升级 +50%）。

**溢出三段效率（v1.4 修订）**：`0–100% = 100% 效率｜100–150% = 50% 效率进暂存区（容量 = 上限 × 50%，round）｜>150% = 0`。
暂存区**必须有独立的库存上限与独立的 UI 显示**，不许和主库存共用一个数字——否则玩家看到"水 18/15"会以为界面坏了。玩家在外时可见屋内库存：≥80% 变黄、进暂存区变红、并显示"预计 N GH 后溢出"倒计时。
3 个维护动作：加燃料（8GH 一箱）、清滤芯/换菌床（脏了产出 -50%）、补料。**连续 3 天不维护 = 断电 = 夜间陷阱全失效**。衰减而不暴死。
净水/食物是背包消耗品由玩家手动吃喝，**不做强制自动投喂**（否则四条状态条失去意义）；L2 可解锁"自动配给"开关作为后期减负。

### 9.5 事件系统

| 类别 | 触发 | 量级 | 影响面 |
|---|---|---|---|
| 随机 | 地点内/出门期掷骰 | 每日 1–2 次 | 数值 / 开关 / 生成 |
| 定时 | 全局日程写死（D3 加油站被抢、D5 停电、D7 最后一趟） | 5–7 个 | 开关 / 压缩时间 / 数值 |
| 条件 | 状态/科技/存量触发（净水<5 → 邻居求水） | 每局 8–12 次 | 开关 / 数值 / 生成 |
| 夜间袭击 | 阶段 B 每晚 1 波；阶段 A D4 起 30% | 7 波 + 0–4 次 | 生成 / 数值 |

**存档回滚规则**：事件一旦触发即落盘，当天内不可回滚；存档点为**每日清晨单点自动存档（阶段 A 05:00 / 阶段 B 06:00）** + 退出时保存到同一档；无多档位；死亡从当日清晨重开，种子按「局种子+天数」派生 → 同一天重开随机内容完全一致。

### 9.6 地图与资源

9 类地点：超市、加油站、百货大厦、五金店、药店/医院、警察局、住宅楼、郊区农场、地铁与地下车库（+ 无线电站作为结局 A 前置，条件事件后出现）。
**单地点是独立小场景**（一屏到三屏，图块复用），不是开放世界；安全屋也是独立场景。
连接是**一张总览节点图**（节点+连线+距离），**距离 = GH 成本** → 这是时间/体力预算的可视化，也是"今天去不去郊区农场"的唯一决策依据。
资源：进地点时按种子生成"固定分布 + 随机偏移"，搜过即标记；高频地点 D4 起部分回填一次；跨局不继承。

### 9.7 多周目边界

| 跨局保留 | 每局重置 |
|---|---|
| 科技树"知识"（第二局成本 -50%，L1 全开） | 四条状态、背包、屋内设施 |
| 解锁表（新地点/新事件/新结局/难度档） | 地图搜刮与回填状态 |
| 统计与成就、外观立绘 | 事件进度、天数、夜次、循环库存 |

一句话：**跨局只继承知识、配方和选项，绝不继承强力道具或资源。**

## 10. 分阶段开发路线图

### 10.1 三档划分

# 13. 定稿记录（v1.6 · 与前文冲突处以本章为准）

> 本版经 6 轮交叉审核，累计 38 项变更。技术侧 14 项、设计侧 5 大处、验收侧 2 轮。三位负责人在最后各自独立给出了同一判断：**继续讨论的边际收益已过拐点，该落地了。** 本章即该判断的执行结果——只列变更与口径，不再讨论方案本身。

## 13.1 三条口径（全案最容易被误读的地方）

> **名义 GH**：游戏内时间轴，用于状态衰减、日程、科技研究，**永不换算现实秒**。
> **clock GH**：真实时间驱动的时段，**1 GH = 72 s**。
> **现实时长 = clock GH × 72 s + 压缩时段的实际演出时长**（压缩时段：阶段 A 睡眠、阶段 B 夜间波次）。

一局 **4.51–4.75 h**（纯玩法，无死亡通关）；墙钟 **5.5–6.2 h**（含重开与加载）。需求里的「3–8 h」按墙钟成立。

## 13.2 已生效的关键修订

| # | 修订 | 为什么（一句话） |

| 2 | **阶段 B 全阶段常锁 00:00–24:00**，`20:00` 在阶段 B 不使用 | 门锁状态与波次状态必须是同一个开关，否则会出现"门还开着丧尸已进屋" |

## 13.3 不可操作循环禁令（硬不变量）

> **任何情况下，玩家都不得进入"无法操作但仍在持续受损"的状态。** 一旦出现，无论规则本身多正确，判阻塞缺陷，不许进下一阶段。

落地形态：每夜最多 1 次失能（睡 2 GH 回 20% 体力）→ 第 2 次起进 DeBUFF（体力锁 5%、移速 ×0.6、无法挥砍翻滚，但**能走能吃能喝能进门**）→ 吃正餐解除。

**这一条挡掉的是这样一条链**：20:00 锁门外 → 强制野睡回 0 体力 → 醒来仍 ≤5% → 立即再触发 → 再扣 15 HP → **玩家完全无法操作，看着自己躺死**。原设计里这个漏洞能在一夜之间把 70 HP 的玩家直接打死。

| **夜间波次** | 18:00–次日 06:00 | ❌ | ✅ 从 `wave_start_gh` 起 | 是（同上） |

## 13.6 验收口径（三处已裁定）

1. **P11 跑三组**：① 同种子 20 次 → 验确定性（HP 结余**极差 ≤ 2pp**，超出即有隐藏随机源）；② 20 个不同种子 → 验平衡（**中位数 17%，区间 14–20%**）；③ 只允许整点挥砍次数结算，禁用均值口径（均值会让余量虚高 7pp，等于藏风险）。

3. **`event_log` 是唯一可信事实来源**；`state_contract` 与 `field_catalog` 必须由同一生成器产出。

## 13.11 最后一次修订：撤销一个指标（v1.12）

### 撤销"阶段 B 拆解挤压 %"，改成函数 + 锚点表

这个指标报了 5 次、错了 5 次（24 → 42 → 40–49 → 37–49 → 49），**每次错法相同**：它是 `带入 3–13 件` 这个变量的取值，却被当成常量报了出来。

> **判据：一个指标如果有 5 个版本的修正史，那它需要的不是第 6 版，是换形式。**
> 单值会骗人（42%），区间也会骗人（40–49%，上界仍靠"通常值"）——**只有函数 + 完整边界不会。**

**最终形态不是百分比，是三个式子**（百分比本身会给出错误印象，因为"带入量"与"研发需求"反向耦合）：

```
挤占 GH   = 15.5 + 2 × ceil(max(0, 38 − 带入) / 3)
研发窗口  = 84 − 挤占 GH
总压力    = 挤占 GH + max(0, 剩余节点研发耗时 − 研发窗口)
```

- 带入 0 → 挤占 49.4%，但他阶段 A 已解锁最多节点，**研发需求最轻**
- 带入 30（库存上限，储物升级后）→ 挤占 25.6%，看着轻松，**实际科技树全是坑**
- **只有第三行 `总压力` 才是"这局紧不紧"的答案**

**量纲澄清（第 9 次同形错误的修正）**——三个数被混用过，必须分开写：

| 量 | 含义 | 数值 | 受什么约束 |
|---|---|---|---|
| **带入件数 N** | 本次出门从屋里背出去的件数 | **0–24** | 背包容量 24（固定，不随储物升级变） |
| **零件库存上限** | 屋里能囤多少零件 | **20（基础）/ 30（储物升级后）** | 储物升级 |
| **一次出发携带** | 同上 N，历史表述 | **0–24**，不是 9–13 | 旧文"9–13"是早期估的典型值，不是上限 |

→ **挤压函数的定义域只能是 N ∈ [0, 24]**，故区间为 **25.5% – 49.4%**；`N=30` 那档**不可达**，从表里删掉。
→ **D8 基线"零件 21–25"必须附前置"已解锁储物升级（上限 30）"**，否则与基础上限 20 自相矛盾——这是三个自相矛盾的数互相打架，不是一个数错。

**取整一律显式写实现式**：`floor` / `ceil` / `floor(x+0.5)`，**禁止语言内建 `round()`**——不同语言/版本的舍入模式不同，而这类差异不报错，只会让 0.5 边界悄悄偏一格。

### 谁验算产出（本轮逼出来的角色，我定）

设计侧这一轮**撤回/更正了自己 6 个结论**（4.5h→4.2h、5.5h 不可达、L1=6、≤14 节点、37–49% 区间、5.5h 上限），**没有一条是自查发现的**。他自己的结论是："我在这套流程里的角色是产出，不是验算。"

架构侧同样：8 处实质错误，全部由对方发现。

所以不设"自查要求"（没用），设**交叉验算角色**，且**按盲区形状分工，不按职级**：

| 产出方 | 验算方 | 验算内容 | 只看什么 |
|---|---|---|---|
| 设计侧（玩法数值、成本表、时间账） | **架构总监** | 量纲、勾稽、边界取值 | 只看**结果表**，不看推导 |
| 架构侧（模块契约、性能预算、容量账） | **设计总监** | 玩法语义、状态机可达性 | 只看**结论**，不看实现 |
| 验收侧（判据阈值、容错带） | 双方各一半 | 阈值是否来自可算的推导 | 只看**阈值与依据的对应** |

**铁律：验算方绝不看推导过程。** 看推导会顺着作者的思路走一遍，等于复核了"作者的逻辑"而不是"表本身"；只看结果才逼出量纲与勾稽。

**并且验算方必须有"退回权"，产出方不得申辩"我算过两遍"。** 两遍同源复算只会复现同一个错。

### 三条流程纪律（本轮沉淀，进《制作交付说明》）

1. **交叉复算**：跨系统数值表必须由非作者复算，且复算方**只看结果、不看推导**（看推导会复核"作者的逻辑"而不是"表本身"）。
2. **列名带 (域, 单位)**：任何表格的数值列必须标注如 `front_door_walker(只)`、`陷阱成本(零件)`、`修门耗时(GH)`。引用上游列时**先问域和单位，答不出来标"无法复算"，不采信也不采信其反推值**。
3. **跨侧交界洞双方各写对方风险**：交界缺陷的成因是"双方都想到自己的规则、都没想到对方"，所以自己一方想不全是结构性的，不是不努力。

### 计错账（这比 80 条判据更能说明该由谁复核什么）

| 方 | 实质错误 | 共同形状 | 结论 |
|---|---|---|---|
| 设计侧 | 5+ | 表内不一致 + 自造单位 | — |
| 架构侧 | 7 | **4 处是"凑总数时漏项"**（明细表 7/7 全对） | 明细自己算，总数由别人逐项加 |
| 验收侧 | 2 | **都在"别人的输入"上，不在自己的算式上** | 上游的列由他核域与单位 |

**两个自查结论合起来说明一件事**：每个人都有一个**特定形状**的盲区，而不是"不够仔细"。所以复核分工应该按形状分，不是按职级分。

### 关于"检查者也要被检查"

这一轮出现了验收方两次误报（净水漏原料、天台分母取错子集），它每次都主动撤回并写清错因。**一个会误报但会撤回的检查者，比一个从不误报的检查者可信**——因为后者的"从不误报"往往意味着它没在真检查。

> **能被核对发现的错，都是两个数对不上的错。活得最久的错，恰恰是两个数对得上的错。**（设计侧本轮总结）

本轮所有漏掉的错，确实每一对都"对得上"：5.45 与 5.49、24% 与 17%、8 与 11、12 与 13。
**所以流程要防的不是"算错"，是"两个错互相印证"。** 唯一手段是**第三方用不同方法算同一个数**——同方法复算只会复现同一个错。

## 15. v1.13 裁决与终版口径

### 15.1 P1 定稿（三条，我裁：采用设计侧单阈值版，否架构侧双阈值版）

| 编号 | 定义 | 数值 | 性质 |
|---|---|---|---|
| **P1（硬）** | **`T` 完全退出判定，改数 clock GH + 结构量**（终版） | ① `clock GH == 189 + 9k`（k = 熬夜夜数，0≤k≤2，±0）② `k == 0` 时 `L_fast ≥ 3.31 min` ③ `T` 只记录不判 | 阻塞，防回归 |

**为什么下限不能用时长判（本轮最重要的一条判据设计经验）**：
下限余量 0.02 h = **1.2 分钟**；而一次场景切换 + 淡入淡出累计 **1–2 分钟**。**余量 ≈ 测量误差本身。**
实机测出 4.21 还是 4.19，取决于测量时那台机器在不在跑别的程序——**这不是判据，是抛硬币。**

> **"噪声里的判据"比"错的判据"更坏**：错的判据会被驳倒；噪声里的判据会随机通过、随机失败，最后被贴上 `flaky` 标签忽略——**而 flaky 判据会连它要抓的真实缺陷一起被忽略。**
> 通用规则：**凡"边界余量 < 3 × 测量误差"的判据，一律改写为"某结构量 ≥ 某阈值"，不许用累计量直接判边界。**

`L_fast`（单场夜战最短时长）由整数帧决定，噪声≈0，可直接判。若实测 `L_fast < 3.31`，该局归 P1-obs2 观察项，**不算 P1 失败**——那是"玩家打得太快"，不是"内容不够"。

三条时钟路径对照（用于核对值域，不要再从别处取数）：

| 路径 | 阶段 A | T(L=8) |
|---|---|---|
| 均跳夜 | 126 min | 4.75 h |
| **混合（5 跳 + 2 熬夜）** | 147.6 min | **5.11 h** |
| 全程不跳夜 | 201.6 min | 6.01 h |

> **上限余量 0.39 h（宽松），下限余量 0.02 h（真紧）。P1 的成败取决于下限。**
| **P1-B（观察）** | 全程不跳夜（极端策略） | 5.48–6.01 h | 只记录，不判 |
| **P1-obs2（观察）** | 速通（夜战 <5 min） | 下限可低至 4.2 h 附近 | 只记录，不判 |

**需求口径必须加的 6 个字：「跳夜为主」。** 不加这个前提，将来有人不跳夜跑了 5.9 h 来质疑，我们说不清。

**为什么不采用架构侧的双阈值（硬 4.2–4.8 / 观察 ≤6.1）**：两种拆法都对，但双阈值意味着**两条线都要维护**，而其中一条（4.8）只覆盖"均跳夜"这一种玩法路径，玩家真实分布里"混合跳夜"才是主流——**用一个 5.5 覆盖两种主流路径，比用两条线分别管两种，更不容易在实现里跑偏。**

**为什么不用杠杆调整**：值域算下来，5.5 h 覆盖了"均跳夜"与"混合"两种路径的全部范围，**只有"全程不跳夜"这一种极端策略会超**，而那正是 P1-B 要观察的东西。砍阶段 A 夜间到 5 GH 能省 44% 生存压力，**用平衡换数字，本末倒置**。

> **P1 衡量的是"完成一局核心内容要多久"（设计承诺），不是"玩家最久能玩多久"（玩家选择）。**
> 与 D23（不设夜战最短下限）是同一逻辑的两端：**下限不卡快的人，上限不卡慢的人。**

### 15.2 挤压函数的定义域（第 10 次同形错误，我锁死）

架构侧在写"给数值加单位后缀"那份补丁时，自己又把两个量混了：`带入件数上限 = 零件库存上限（20/30）`。**这两个不是一个量。**

| 量 | 域 | 上界 | 由什么决定 |
|---|---|---|---|
| 带入件数 N | 件 | **24** | **背包容量**（固定） |
| 零件库存上限 | 件 | 20 / 30 | **屋内储物升级** |

→ `N ∈ [0, 24]`，挤压区间 **25.5% – 49.4%**。`N=30` 那一行不可达，删。
**讽刺但必须记下**：这个错出现在一份专门为消灭此类错误而写的补丁里。**说明单靠"意识到问题"不够，必须有机械约束**——这正是下面那条后缀校验存在的理由。

### 15.3 三条已被采纳的机械约束

1. **数值键必须带单位后缀**：`wall_repair_cost_parts` / `wall_repair_duration_gh` / `iframes_ticks` / `store_cap_milli`。
   `validate_data.py` 强制校验，不匹配 `_(gh|milli|ticks|parts|hp|count|px|pct)$` 即 `exit 1`。
   **这样"把零件当 GH 相加"在字面上写不出来**——`_parts` 和 `_gh` 拼不进同一个变量名。标注靠人看，后缀靠校验器。
2. **两份《对方风险》同时封存、必须署名**：写完不提交，双方都写完一起开。匿名互评在熟人之间一定退化成客气话；署名把"随便写两句"变成"我要为这个判断负责"。
3. **取整一律写实现式**（`floor` / `ceil` / `floor(x+0.5)`），**禁用语言内建 `round()`**——舍入模式差异不报错，只让 0.5 边界悄悄偏一格。

## 17. 终局：一条判据与四条数值纪律

### 17.1 这轮最值钱的发现：余量的方向反了

**六轮都在为 P1 的 5.5 h 上限吵，但上限从来没被逼近过。真正只剩 0.02 h 余量的是下限。**

| | 我们以为 | 实际 |
|---|---|---|
| 余量在哪 | 上限 5.5（只差 0.05 h） | **下限 4.2（只差 0.02 h）** |
| 最接近的路径 | 不跳夜 | **熟练玩家三夜速通（4.22 h）** |

而当时已经提上桌的处置方案是"砍阶段 A 夜间 9 GH → 5 GH"——**为一个不存在的风险，削掉 44% 的生存压力**。架构侧那句自评是准的：「**基线错 → 针对性设计 → 实测发现基线错。这个循环很贵。**」

> **判据：任何"要不要动平衡去迁就验收线"的决定之前，先算清余量在哪一侧。余量的方向比余量的大小更重要。**

### 17.2 四条数值纪律（本轮唯一沉淀，比任何数值耐用）

1. **报数标方向**：`21（偏高）` / `11（偏低）`。**没标方向的数，就是"下一轮会被误标方向"的候选。**
   本轮实例：17（偏高）→ 实测 21 是往上跳；11（偏低）→ 实测 15 是往下跳。**方向决定最坏后果**：17 偏到 21 会让 6 夜提前死，11 偏到 15 会让 D3 就能修满血。
2. **三段式键名**：`{域}.{ID}.{量}_{单位}` → `reversal.serum.research_gh` / `trap.spike.cost_parts`。
   字符串带 `_gh` 就写不进 `_parts` 变量，**这是唯一能量产的拦截点**。
3. **取整一律显式写实现式**（`floor` / `ceil` / `floor(x+0.5)`），禁用语言内建 `round()`。
   理由从"编辑器不友好"改成更硬的：**不同语言/版本的舍入模式不同，而这差异不报错，只悄悄偏一格**。
4. **所有上限类数值必须附前置条件**（`store_cap_parts ≤ 20，前置：未解锁储物升级`）。
   `D8 基线 21–25` 与"上限 20"打架，根因就是上限没附前置——**三个数各自正确，放在一起矛盾**。

### 17.2.1 数值错误分三层，这轮的 8 处分布在三层

| 层 | 错误形态 | 本轮实例 | 处置 |
|---|---|---|---|
| **名字层** | 同一个键名指向不同的量 | `store_cap` 同时指"带入上限"和"屋内库存上限"；`research_gh` 与 `research_hours` | 三段式键名 + 后缀校验 |

### 17.2.2 两条通用判据（交付后仍然适用）

1. **偏差方向标注**：报数必须标"偏高/偏低"。
   **错的悲观估值比错的乐观估值危险得多**：乐观的 4.2 会让流程早一点暴露问题（实际 4.22，差 0.02 h，无害）；悲观的 4.2 差点引出"砍阶段 A 夜间"这个真会破坏设计的动作。**乐观自己会暴露，悲观会驱动动作。**

2. **噪声里的判据比错的判据更坏**：
   凡"边界余量 < 3 × 测量误差"的判据，一律改写为"某结构量 ≥ 某阈值"。
   错的判据会被驳倒；**噪声中的判据会随机通过随机失败，最后被贴 `flaky` 标签忽略——而 flaky 判据会连它要抓的真实缺陷一起被忽略。**

### 18.7 C27：时间系统的唯一真相是整数帧计数器（实现级变更）

**起因**：P1 要改成 `clock_GH = 189 + 9k` 的 ±0 判定，但 v1.0 的实现是 `gh += delta_sec / 72` 的 **float 累加**——189 GH = 816,480 帧，81 万次累加后无法断言全等。

```gdscript
var elapsed_ticks: int          # 唯一真相：单调增整数，永不 float 累加
func gh() -> float:             # GH 是纯函数派生，不存储
    return float(elapsed_ticks) / 4320.0

const FRAMES_PER_GH         := 4320    # 72 s × 60
const FRAMES_PHASE_A_DAY    := 64800   # 15 GH
const FRAMES_SIEGE_DAY      := 51840   # 12 GH
const FRAMES_NIGHT_OVERTIME := 38880   # 9 GH
```

| 项 | 帧数 |
|---|---|
| 阶段 A 活跃（7 天） | 453,600 |
| 阶段 B 白天（7 天） | 362,880 |
| **合计** | **816,480 = 189 GH ✓** |
| 每个熬夜夜 | +38,880 |

**P1 于是变成真正 ±0**：`elapsed_ticks == 816_480 + 38_880 × k`（整数全等），`T` 纯导出、只记录不判。

> **收益比 P1 本身大**：`gh` 不再 float 累加 → **"帧率不同导致 gh 漂移"这一整类问题从根上消失**；P7（读档 diff = 0）也不再依赖"浮点足够精确"这个假设。
> **这也是唯一一次"为了把判据做对，顺手改对了实现"**——判据需求反过来暴露了实现缺陷，这个方向通常不会发生。

**存档 schema 相应改动**：存 `time.elapsed_ticks`（int64），**不再存 `gh_total` / `gh_elapsed_today` 浮点**。`gh` 字段若保留，只作派生缓存且不参与 hash 比对。

### 18.8 第 0 层：写表达式（比三层更可操作）

> **取任何一格之前，先把它写成含域限定名的表达式**（`round(front_door_walker × 0.2)`）。**写不出来的格子，就是没定义清楚的格子。**

它排在三层对策之前，因为：零成本、当天可用；写表达式时被迫写全名（域与单位自己浮出来）；写不出来就说明这个数不该用于决策。

**它直接对症 18 处错里 13 处的共同动作——从二维表里取数。** 取错格子的人只要被迫写一遍表达式，就会看见自己取的是哪一格。

**以及一条改写判据的硬要求**（只写第一条等于换了个更精确但覆盖更少的判据）：
```
① 原判据的哪些分支被结构量覆盖
② 哪些分支没被覆盖
③ 为什么没覆盖也不需要覆盖（恒满足 / 已转观察项）
```
> **"看起来更严谨"是最危险的伪装形态**——和"区间看起来已经考虑了变化"（37%–49%）是同一族。

### 18.9 一处措辞纠正（结论对、理由错会被推翻）

QA 曾写"全程不跳夜在任何情况下都不可能满足 5.5 h 上限"。**精确说法**：k=7 时要求 `L ≤ 3.66 min`，而 `L=3.5` 存在，故 `T = 5.48 h ≤ 5.5` 可满足——**是"典型情形必然超"，不是"数学上不可能"。**

`5.77 h` 的隐含前提是 `L=6`，不写出来就变成"必然"。**这正是"报数标方向"要防的东西，而刚立完这条就又犯了一次。**

## 19. C28 与第四种死法（终稿）

### 19.1 能消灭冗余，就不要校验冗余

前 17 轮我们一直在**加校验**：三层数值对策、F0、F0-b、双向校验、裁断规则。第 18 轮第一次做**减法**。

**问题**：基线表同时写帧数与秒值（9/8/6/12/216 帧 与 0.15/0.12/0.10/0.20/3.60 秒），`windup` 的 8 帧 = 0.1333 s 与写的 0.12 s 差 13.3 ms → F0-b 从第一天起永远红 → **永远红的判据最后会被关掉，关掉之后它防的事就没人防了。**

**解法不是"改一下秒值"，是删掉这个来源**：
```
基线表只写帧数（权威：9 / 8 / 6 / 12 / 216）
"≈ 秒"那一列由 tools/gen_baseline.py 从帧数生成
→ 不一致在物理上不可能发生
```

> **能消灭冗余，就不要校验冗余。**
> 校验的价值上限是"发现不一致"，消灭的价值是"不可能不一致"。
> **先问"第二个来源能不能不存在"，能就删；删不掉（因为它承载不同信息）才校验。**

这条修正了前两轮的方向：**"单来源无法自证错"是对的，但它的推论不是"所以要两份来源"，而是"来源本身不该是手写的"。** 我们前两轮直接跳到"校验"，只走了一半。

### 19.2 判据的四种死法 + 一条规范条款

| 死法 | 症状 | 处置 |
|---|---|---|
| **自洽** | 两个数写在同一文件，永远相等、错得一样 | 独立第二来源 / 删冗余 |
| **不同步** | 改帧数没改秒数，永远红 | **删冗余**（生成而非手写） |
| **单来源** | 代码写 7、F0 也写 7，无法裁断 | 裁断规则：以帧数为准 |
| **④ 存量未清** | 规则立了，老数据还留着 | **立规范时必须同轮清存量** |

> **第四种的毒性在于：立规则的那一刻看起来事情已经解决了。**
> "以后只给帧数"听起来问题已关掉，但五个老秒值还躺在表里——**规则是承诺，不是动作。**
> 条款：**立任何字段规范时，必须同轮给出「存量清单 + 清理动作」，否则条款不生效。**

### 19.3 科技树四列并列表（数量类修订的标准格式）

| 层 | 基线 2.3（区间估计） | 实际铺开 | 砍除 | 定稿 |
|---|---|---|---|---|
| L1 | 6 | 6 | L1-6 背包扩容 | **5** |
| L2 | 8–9 | 9 | L2-2 绊索、L2-3 燃烧瓶 | **7** |
| L3 | 9–10 | 10 | L3-5 保温层、L3-10 空气循环 | **8** |
| L4 | 5–6 | 6 | L4-5 净水大改、L4-6 隔音加固 | **4** |
| — | 28–31 | **31** | 7 个 | **24** |

**验收侧找不到 L3/L4 差额，是因为设计侧给了"砍哪几个"和"每层最终数"两张分开的表，让它自己拼**——而两张表之间的拼合，正是这一轮所有错误的共同形状。

> **标准格式：任何数量变化必须一张表四列给全（估计 / 铺开 / 砍除 / 定稿），不许拆成两张表让人拼。**

### 19.4 一处我（制作人）推错的更正

我曾依据架构侧判断写下"L4 需 L3 任两节点更容易满足 → 阶段 B 科技压力下降"。**这是错的**：前置条件是 `L3 任两节点`，**与 L4 有多少节点无关**。节点数只影响 L4 的**可选集**，不影响**可达性**。

砍节点的真实代价是另一件事：**单局覆盖率从 39–52% 升到 50–67%，多周目重玩价值变薄**（每局漏掉 48–61% → 33–50%）。**所以 24 是下限，不许再砍**——再砍下去一局能全开科技树，直接摧毁"多周目解锁"这个核心卖点。

## 20. 收口：P1 终式、M28 机械约束、两条新原则

### 20.1 P1 的最终判定形式（整数全等）

```
P1（硬）① elapsed_ticks == 816_480 + 38_880 × k   （整数全等，±0）
        ② k == 0 时 L_fast ≥ 3.31 min；k ≥ 1 无下限约束
        ③ T 是纯导出量，只记录，不判
```

`k` = 熬夜夜数，定义域 `k ∈ [0, 2]`（跳夜为主 = 7 夜中至少 5 夜跳夜）。三档前置校验必须显式断言，否则 k 会静默越界。

**P1-B 归观察项的理由改成「前提排除」**：
> 依据是**"不属于 P1 的适用域（k ≥ 3）"**，不是"它不可能满足"。

**强度差一个量级**：前者是适用范围的声明（不需证明任何数值性质），后者是数值不可能性的断言（**找到反例就崩**——`L=3.5` 时 k=7 的 `T=5.48 h` 就满足）。

**并由此得到一条判据设计依据**：强行纳入会得到一个**在同一路径上随 L 分裂**的判据（L≤3.66 过、>3.66 不过）。**"同一路径有时过有时不过、且分界取决于另一个变量"的判据，是最难向玩家和团队解释的形态。判据的形态本身应当成为决策依据。**

### 20.2 M28「同一事实只定义一处」的机械写法（不用登记表）

> **凡带单位后缀的 key（`*_gh` / `*_parts` / `*_ticks` / `*_hp` / `*_milli` / `*_count` / `*_units` / `*_px`），全项目 `data/**` 内只能出现在恰好 1 个文件里。**

约 15 行：遍历所有 json，收集"单位后缀 key → 文件集合"，任一 key 命中 ≥2 文件即 `exit 1`。

**为什么够用**：**定义 = 带单位后缀的数值 key**（承载一个量）；**引用 = 字符串 id 值**（指向别处）。所以"同一事实两处定义"必然表现为"同名单位 key 出现在两文件"。**这个写法不需要知道谁是 owner，只需知道"只能有一个"。**

**这是 C28 原则的第一次机械落地**——从"要有人记得别写两处"变成"写两处就红"。**登记表会退化成"谁报错谁加"，和域白名单一个下场。**

### 20.3 秒值不再手写（C28 的落地形态）

```
权威源：data/balance/combat.json 只存帧数（9 / 8 / 6 / 12 / 216）
生成物：tools/gen_baseline.py 从帧数产出"≈ 秒"列
规则：文档禁止手写任何秒值（人工写入 = CI 拒绝）
```

**设计侧补的理由比技术理由更硬**：**校验规则需要有人一直维护，生成脚本不需要。** 一人项目里这条差别是决定性的——**病两个月回来，校验规则还在但那两个月没人执行；生成脚本则一直是对的。**

### 20.4 两条新原则

**① 全称判断必须附反例搜索记录**
> 凡写"必然 / 不可能 / 唯一 / 总是"，必须附反例搜索记录（试了哪些值、都不成立）。**写不出来就降级为"典型情形下"。**

**适用范围**（防形式主义）：只需覆盖**结论所依赖的那个自由变量的端点**，不必穷举。例："k=7 不可满足"只需试 `L ∈ {下限, 典型, 上限}`，L=3.5 一算就破。
**错账佐证**：QA 6 处错里 3 处是"没验反例"，架构 9 处里 2 处同族。

**② 工具优先级按"错误反馈延迟"排序，不按成本排序**
> **成本低只说明"值得做"；反馈延迟说明"不做就会带着错往下走"。延迟长的错不会自己消失，只会变大。**

这就是"第 0 层写表达式"该排在三层之前的真正原因——**不是因为它便宜，是因为它唯一一个"错的时候会当场疼"。**

### 20.5 24 处错账（19 轮统计）

| 形状 | 次数 | 占比 |
|---|---|---|
| **从二维表取数 / 取错格子 / 列行不一致** | **13** | **54%** |
| 全称判断未验反例 | 5 | 21% |
| 区间边界未算全 | 4 | 17% |
| 选错定义后正确推导 | 1 | 4% |
| 其他 | 1 | 4% |

**一半以上是同一个动作。** 对策已成链：**第 0 层（写表达式）→ 名字层（键名三段式 + 域白名单）→ 数值层（分项 / 全边界）→ 决策层（可测性优先）**。M28 是其中第一个"写两处就红"的机械约束，**在此之前全部靠人**。

### 20.6 float 残留面收敛到 4 个字段

被三条独立需求各推一次的结果：产线定点（设计侧）→ 时间改帧计数（±0 需求）→ 库存改 milli（类型断言）。

现在还用 float 的只有 **HP / 体力 / 饥饿 / 渴**，**且全部不参与 L1 判定，P7 允许 ±0.5 容差**。

> v1.0 里 float 遍布状态、库存、时间、帧数；现在只剩四个连续速率量。**这个收敛不是设计出来的，是三条独立需求各推一次的结果。**

### 20.7 科技树 7 个砍除节点的完整清单

| 原编号 | 节点 | 砍因 | 去向 |
|---|---|---|---|
| L1-6 | 背包扩容 I | 与 L2-5 储物升级重复 + 纯数值 | 删（并入） |
| L2-2 | 绊索陷阱 | 与尖刺陷阱重叠 | 删 |
| L2-3 | 燃烧瓶 | **投掷远程与"近战为主、枪械稀少"冲突** | 删 |
| L3-5 | 保温层 | 纯数值（+30%），玩家感知不到 | 删 |
| L3-10 | 空气循环 | 需开新事件域（毒气），超出 4 类能力 | 延后 |
| L4-5 | 净水大改 | 与 L3-2 净水器重复 | 并入三级升级 |
| L4-6 | 隔音加固 | 需改波次生成逻辑，与加固门/天台重叠 | 延后 |

**7 个只有 4 类理由**：功能重复 3 / 纯数值 1 / 与核心定调冲突 1 / 需开新系统域 2。
**这四类反面可以当"加节点"的自查表**：有独立动词、能被感知、不冲突定调、不依赖新系统——四条都满足才该进树。

### 20.8 数值索引（治"改了没同步"）

**诊断**：这轮三方共 **9 次"改了没同步"**（L1 6→5、5.48 放错行、windup 7→8、tech 31→24、判据 42→46…），**没有一次是"忘了去查"，全部是"没有清单可查"** ——因为**你无法枚举"所有地方"**。

索引已交付 16 条高风险数值（数值 / 权威源 / 引用处），覆盖：时间基准、科技 24、战斗 5 常量、库存与存零件上限、饥渴速率、阶段 A 时间结构、`day++` 时刻、阶段 B 窗口、材料需求 38、夜 7 有效 HP、7 夜构成、野睡、失能、体力预算。

**两条规则，第二条比第一条重要**：
```
1. 改数值前先查索引，改完按索引逐处勾掉
2. 新数值入库时，若它已在 ≥2 处出现而索引里没有 → 索引不完整，拒绝入库
```
> **索引不能只在"改的时候"维护，必须在"加的时候"就拦。** 否则新数会绕过索引，而绕过索引的数正是下一轮"没同步"的来源。

### 20.9 M28 的边界：数量可以声明，重算值不行

| 写法 | 判定 | 理由 |
|---|---|---|
| `trap_budget = 3` | ✅ 合法 | **数量声明** |
| `trap_damage_total = 600`（在 waves.json） | ❌ 违规 | **重算值**（= 3 × 5 × 40），应由 budget × uses × damage 导出 |

**这条直接治住了 `trap_spike` 双定义**——它让一条判据（`3×5×40=600`）踩在"两个文件都能定义"的坑上。**非法值会报错，重复定义不会报错，只会让两个源慢慢分叉。**

### 20.10 全称断言必须附枚举记录

**实证**：设计侧这轮三处全称断言，**两错一对**，区别就是那处对的真的枚举了取值：

| 断言 | 结果 |
|---|---|
| "5.5 h 上限结构上不可达" | ✗ 只在不跳夜时不可达 |
| "银行家舍入会让某批翻" | ✗ 造了一个不存在的批次 |
| "夜 7 承伤只能取 62.25 / 83.00" | ✓ 真枚举了 hits = 3 或 4 |

**规则**：凡写"只能 / 必然 / 唯一 / 不可达"，必须附枚举记录；列不出来就降级为"典型情形下"。

## 21. 一句话收尾

`F0-b` 第一次红的真正意义，**不是"发现了一个 bug"——它抓到的是基线，不是代码。**

> **代码错了会崩，基线错了不会崩，只会让所有人按错的数干活，而且每一份产出都看起来对。**

这就是为什么这套东西的验收标准是"第一次跑至少要红 2 条"，而不是"全绿即通过"。

## 22. 最后一条风险与一条门禁资格规则

### 22.1 R11：阶段 B 存在"玩家不可知的必败路径"（我裁定：必须消除）

**成因**：拆解台是阶段 B 材料链的唯一来源（所以被列入"破防不可拆"），而阶段 B 出不去、材料只减不增。**玩家若在 D7 结束前没解锁拆解台，阶段 B 就是必败局**（夜 6 起零陷阱必死）。

**为什么我不能接受**——不是难度问题：
> **必败路径最恶劣的地方，是玩家在 D1–D7 完全不知道自己已经输了。** 他会继续投 2 小时，然后在夜 6 被无预警打死，并把这读成"数值崩了"而不是"我 D3 点错了科技"。

**处置（终版，我原提的"每天产 1 零件"已被否决）**：
1. **浅化前置**：拆解台前置压到 **L1 任一节点**（不依赖 2 个以上 L2）
2. **自动补授**：**D8 06:00 若仍未解锁 → 自动补授（不耗材料与时间）+ 一句叙事字幕**

**为什么否掉"阶段 B 每天产 1–2 零件"**：那会改挤占函数（每天 +1 零件 = 7 天省 5 次拆解 = 省 10 GH → 挤占从 47% 掉到 35%）。**为一个极端路径动全局平衡不值，而且它会让"没建拆解台"变成"没关系"。**
自动补授只动那条极端路径，**对正常局零影响**（D8 基线玩家必然已解锁）。

> **这条应归入交付说明的"必败路径"一类**：不是所有"难"都是难度。**有些难是设计漏了一条出口，而它在数据上和难度长得一模一样。**

**对应判据**：构造「只点 L1、0 个 L2」的存档直接进 D8 跑满 7 夜。**必须专门造"科技点歪了"的存档**——必败路径的定义是"存在一条可达序列"，不是"典型玩家会走到"。

### 22.2 门禁资格：只有"跑一次型"能当门禁

> **校验规则需要有人一直维护，生成脚本不需要。校验会随人数减少而失效，生成不会。**
> 一个人病两个月回来，校验规则还在、但那两个月没人执行；生成脚本则一直是对的。

| 类型 | 机制 | 能当门禁吗 |
|---|---|---|
| **跑一次型** | `validate_data.py`、`check_deps.py`、M28 扫描、秒值生成、`elapsed_ticks`、`F0` | ✅ 红/绿判定 |
| **每次要做型** | 写表达式、报数标方向、反例搜索、跨侧洞互评、《对方风险》署名 | ❌ 只能进评审清单 |

**理由**：把靠人记的机制当门禁，它的失败会被记成"人没做"——**而"人没做"在门禁里不可归因**。你会看到红，但分不清是实现错了还是流程没走。**一个不可归因的红，最终会被当成噪音，然后被关掉。**

**这条修正了前几轮的倾向**：我们加了 9 条纪律，其中至少 2 条（报数标方向、反例搜索）**根本进不了 `test.ps1`**。**加了也不能当门禁，只能当审查项。**

### 22.3 技术债：科技树重编号的旧引用

设计侧保持 `L2-1 尖刺` 不变（决定对，它被引用最多），但 L2 的 2–9 全部位移，基线里散落旧编号。已确认 4 处错位：

| 基线写的 | 新编号 |
|---|---|
| `L2-4 发电机` | L2-2 |
| `L2-8 天台` | L2-6 |
| `L2-9 拆解台` | L2-7 |
| `L3-9 培养槽` | L3-8 |

**后果**：会出现"L2-4 是加固门，但基线说它是发电机"。**待补完整新旧映射表（含已砍标记）。**

> **教训**：用例与代码**不要引用节点编号，引用语义 key**（`unlock_dismantle_bench`）。**编号是标识符，它已经改过一次，还会再改。**

### 22.4 判据的方向失衡：3 : 81（这条解释了"全都对，但玩不了"）

84 条判据里：

| 方向 | 条数 | 例子 |
|---|---|---|
| **验证推导**（数 → 结果） | **81** | 饥饿 100 s 死、夜 7 结余 17%、读档 diff = 0 |
| **验证源头**（数本身对不对） | **3** | F0-b 帧数↔秒数、M28 双定义、C28 秒值生成 |

> **3 : 81。而源头错的影响面是全局的——"验证能力"的分布和"错误影响面"的分布正好是反的。**

这解释了一个古怪现象：**每份文档都对、所有自检都过、然后游戏不能玩。** 因为错误在"所有人共用的那个数"上，而不在任何一份产出里——每份产出都是"从那个数正确推导"的，所以每份都对。

**补救（只能部分救）**：上游每个关键基数都附一行 `report_number` 记录（值 / 域 / 单位 / 偏差方向 / 反例搜索）。**这是审查型，不是门禁型，所以只能救被抽查到的那部分。**

### 22.5 交付后看报告的正确方式

「门禁全绿」覆盖的东西**比字面少得多**：

| 类型 | 本项目的条数 | 绿了意味着 |
|---|---|---|
| **机器判定（跑一次型）** | **5 条** | 真的绿了 |
| **人工审查（每次要做型）** | **7 条** | 只代表"这次做了"，不代表"下次也会做" |

> **两份报告必须分开写，绝不合并成"纪律全绿"。** 一个不可归因的红，最终会被当成噪音，然后被关掉。

### 22.6 判据投入应往源头侧倾斜 + 三档优先级

把 24 处实际错误按侧分：

| 错误侧 | 数量 | 例子 |
|---|---|---|
| **源头侧**（基线/定义/引用旧版/单位混算/编号位移） | **约 12 处（100%）** | 零件当 GH、L1 6→5、5.48 放错行、tech 28–31、windup 0.12、编号不连续、trap 双定义 |
| **推导侧**（实现偏差） | **0 处** | 还没开始实现 |
| 判据投入 | **96% 在推导侧** | 81 条 vs 3 条 |

> **100% 的实际错误在源头侧，96% 的判据在推导侧——两者几乎正交。**
> **这解释了为什么这一轮所有错误都是人肉抓出来的、没有一条是判据抓出来的**：不是判据写得差，是**它查的方向和错误发生的方向不同**。

**5 条源头侧判据（均可机械，已交验收侧）**：

```
S1 四列算术一致：原先 − 砍除计数 == 最终     → 抓"31−7=24 对得上，但砍谁没说"
S2 编号引用有效：文档里每个 tech id 必须存在  → 抓"重编号后文档仍留旧编号"
S3 单位后缀完整：数值键必须 域_量_单位        → 抓"零件当 GH"写不出来
S4 索引覆盖：索引说某处有该值，该处必须真有    → 抓"索引本身陈旧"
S5 禁止裸数字：值不得是未标单位的裸数         → 与 S3 互补（键名 vs 值）
```

**三档优先级（这是本轮最好的一个归纳）**：

| 档 | 手法 | 例 | 特点 |
|---|---|---|---|
| **1** | **消灭违规场景**（让违规写不出来 / 用不上） | 判据现算重算值、秒值脚本生成、`progress_milli` 单真相（HUD 只派生） | **往往更便宜且不会漏** |
| 2 | 机械检测 | M28 ①②、域白名单、单位后缀正则 | 能红能绿，可当门禁 |
| 3 | 审查项 | M28 ③、必然型枚举、跨侧洞互评 | 只能进评审清单 |

> **黑名单永远漏，因为违规总是新写法。** 所以优先级必须是"消灭 > 检测 > 审查"，而不是反过来。
> 这一轮我们下意识都从"加校验"开始想——**加了 19 轮，最后最有用的三条（C28、M28、elapsed_ticks）全是"让错误不可能存在"，不是"发现错误"。**

### 22.7 风险清单格式：已缓解 ≠ 已接受

**R11（阶段 B 必败路径）处置定稿**：前置压平（**L1 任一节点 + 3 GH + 3 零件**，那 3 零件是研究成本、不是另加的建造费，所以"解锁即可用"）+ **D8 06:00 未解锁则自动补授** → 判定 **"已缓解，但不销号"**。

> **销掉风险等于销掉那条断言。** 兜底是运行时行为，它本身需要被守护——否则将来有人重构事件系统、或把兜底挪到 D9，不会有人发现，而失效的后果是**极端路径重新变成必败**。

**由此立一条风险清单格式规范**：
> **标"已缓解"必须附守护断言；没有守护断言的只能标"已接受"。**

**"已缓解" = 有机制在防它；"已接受" = 知道它在但决定不管。** 混用这两个词，缓解措施会慢慢腐烂而没人知道——**因为没人再看着它了。**

### 22.8 验收报告必须强制两段（本轮最要紧的处置）

**问题**：12 条验收纪律里 **只有 5 条能当门禁**，7 条只能进评审清单，而原报告把 12 条并列——**会让人以为"全绿 = 12 条都过了"。**

```jsonc
{
  "gate_results":   { "total": 5, "pass": 5, "fail": 0 },
  "review_results": { "total": 7, "done": 4, "not_done": 3,
                      "note": "本区不参与通过判定" },
  "coverage_statement": "本报告覆盖 5 条门禁；另有 7 条审查项不在本报告判定范围内"
}
```

**三条硬规则**：
1. `release` 判定**只读** `gate_results`
2. 报告首页必须印 `coverage_statement`，**schema 层面禁止字段值出现"全部 / 所有 / 全绿"**
3. `review_results.not_done > 0` **显示但不算失败**

**第 3 条是关键**：审查项的价值在**可见**，不在**拦截**。一旦让它拦截，就会走上"永远红 → 被关掉"那条路。

### 22.9 对账成本越低，证明越少

> 两个数对得上，只证明**互不矛盾**，不证明**各自覆盖完整**。**总数对得上是最便宜的对账，而最便宜的对账最常被当成已验证。**

**实例**：`5+7+8+4=24` 与 `6+9+10+6−7=24` 两边都对得上，**所以 19 轮里没人去问砍的是哪 7 个**。

**派生用例规范**：任何"数量变化"的断言必须能列出变化项清单；只能给总数的，标 `无法验证逐项`。

### 22.10 规则有三种死法，第三种不会自己暴露

| 死法 | 症状 | 谁能发现 |
|---|---|---|
| **被删** | 理由不成立（"我看现在没分叉啊"） | 落笔时自问 |
| **被关** | 误报太多（几百个合理历史值把它刷红） | 落笔时自问（→ 必须给豁免区） |
| **被架空** | **规则在、也跑、永远绿，因为写得太松什么都没测到** | **只有变异测试** |

**第三种是唯一不会自己暴露的**：被删和被关都有人看得见（有人在删、有人在关），**被架空的判据一直在跑、一直绿、一直没人管。**

**所以"落笔时问两个问题"变成三个，第三个必须配一个变异体。**

### 22.11 判据有两次缩水，"85 条"这个数不可引用

| 缩水 | 从 → 到 | 靠什么测 |
|---|---|---|
| **第一次**：能否机械化 | 12 条纪律 → **5 条门禁** | 分类时就能算 |
| **第二次**：是否独立覆盖 | 85 条判据 → **？条** | **只有变异测试** |

**第二次缩水完全没有数，而它可能比第一次大**——85 条里真正独立覆盖的可能只有四五十条。**所以"判据 85 条"现在不该被当作成果引用。**

**有意义的数是"变异体能单独杀死的条数"，而那个数只能等第一次变异测试。**

`coverage_statement` 因此升级成三行：
```
本报告覆盖 5 条门禁；另有 7 条审查项不在本报告判定范围内。
这 5 条中，0 条经变异测试确认独立覆盖（本次未做变异测试）。
判据纸面条数 85，独立覆盖条数未知。
```

> **第一次跑就写"0 条确认"，比用 85 撑场面诚实。** 而"0"这个数会让人立刻问"那什么时候做变异测试"——**这正是它该起的作用。**

**变异测试的两条标准**（第二条比第一条更重要）：
1. 目标判据变红
2. **且只有目标判据变红** —— 一个变异体让 5 条全红，看似抓得好，**实际说明这 5 条在测同一件事**

### 22.12 多因判据必须拆

**实例**：`P1` 下限红了，可能是①实现跑太快 ②测量偏差 ③前提未满足（k≥3）——**三种原因一个红，无法处置。**

> **一条判据的红若能对应 N 种原因，它实际是 N 条判据被合并成了一个红。** 合并的后果不是"更简洁"，是"红了以后分不清该修哪一条"。

**规则**：落笔前先数失败原因。**> 1 种就必须拆成「前置筛选 + 单因判定」两级**；前置筛选本身也是判据（如 `M29: k ≤ 2`），**作用是保证进入判定的每一局失败原因唯一**。

### 22.13 科技节点改用语义 key（消灭"重编号"这个事件类）

**起因**：设计侧刚立完"标识符不得编码会变的数据"，下一个 key 就写成 `tech.L2_7_dismantle`——而那个编号他自己刚改过（原 L2-9）。

> **这条规则只在"别人引用"时被想起，在"自己定义"时被忘掉。而定义端才是源头。**

**处置**：24 个节点全部改**语义 key**，编号降级为 `display_order` 显示字段。

```
tech.unlock_dismantle_bench   ← 引用锚点（永不变）
  display_order: "L2-7"       ← 显示字段（可随时改）
```

**这一改把"重编号"这个事件类整个消灭了**：以后增删节点只改显示字段，任何引用都不动，`rename_tech_node.py` 也不用写了。**属于第 1 档（消灭问题），不是第 2 档（检测问题）。**

**需求/基线文档里的 `L2-x` / `L3-x` 编号从此只当显示用，不再作为引用锚点。**

### 22.14 变异测试的预测（用来验证判据是否"看着对"）

预期抓不到的变异体及原因：

| 变异 | 为什么可能抓不到 |
|---|---|
| 文档秒值 `0.1333→0.12` | 若 C28-b 只查"有没有秒值"而不查"秒值与帧数是否一致"，会绿 |
| GH 帧数 `4320→4300` | 若两边都从同一常量读，会一起变绿 |

**共同点：改了定义、所有消费者一起跟着改**——这类变异在一致性检查下是自洽的，**只有绝对值断言才抓得到。**

### 22.15 `prereq` 的 AND/OR 歧义会让 R11 缓解反向恶化

**问题**：设计侧写 `"prereq": ["tech.unlock_manual_water_filter" /* 或 L1 任一 */]`。
**科技树的 `prerequisites` 列表在绝大多数系统里语义是 AND（全部满足）**，而设计意图是 OR（任一）。

| 实现按字面 | 实际门槛 |
|---|---|
| 当 AND | **需 5 个 L1 全点** |
| 填 1 个 | 只需那 1 个（但那就不是"任一"） |

> **而 R11 的缓解措施正是"前置压平到 L1 任一"。实现成 AND，缓解就从"1 个 L1"变成"5 个 L1"——比原来更难，缓解变恶化。**

**最危险的地方**：歧义藏在注释里（`/* 或 L1 任一 */`）。**注释不参与校验，所以它不报错，只会静静按 AND 执行，然后表现为"缓解措施没生效"。**

**定稿：拆成两个字段，禁止单数 `prereq`**
```jsonc
"prereq_all_of": [],                      // 必须全满足，空 = 无前置
"prereq_any_of": [5 个 L1 语义 key],       // 至少满足 1 个
```
**schema 强制**：① 两字段必须都存在（空写 `[]`），禁止单数 `prereq`；② `prereq_any_of` 非空时必须 ≥2 元素（1 个的"任一"没意义）；③ 两字段不得出现同一元素。

**目录级守护**：`unlock_dismantle_bench.prereq_any_of` 集合必须**恰好等于全部 5 个 L1 key**——将来有人改成"任意 2 个"，缓解被弱化，这条会红。

**由此立一条通用规则**：
> **凡"意图"与"数据"分离的地方，意图必须变成字段。注释只能写"为什么"，不能写"是什么"。**

**证据链补一条**：R11 补授若走"解锁事件"通道，会与正常解锁共用路径（记日志/触发成就/播提示音）。**重复补授在正常局不会发生，所以这个 bug 会一直藏着**，直到有人用极端局触发。
```
D8 06:00 若 false → 变 true，授予计数 == 1
若已 true → 授予计数 == 0
```

### 22.16 第 2 次"消灭问题类"（不是检测问题）

设计侧把 24 个节点全改语义 key，编号降为 `display_order`（仅显示）。**这一步把「重编号需同步引用」整个问题类消灭了。**

| 次序 | 事件 | 消灭了什么 | 提出方 |
|---|---|---|---|
| 1 | 秒值由脚本生成（C28） | "两个来源对不上" | QA |
| **2** | **编号降为 `display_order`** | **"重编号需同步引用"** | 设计侧 |

> **每个"检测方案"落笔前先问一句：这件事能不能让它不发生？问不出来再用检测。**

**配套：`tools/rename_tech_node.py` 撤销，但必须留撤销理由**——**一个被撤销的工具如果没有留下理由，它会被重建。**
```
已撤销：tools/rename_tech_node.py
理由：「重编号需同步引用」问题类已消灭，工具无必要
若将来重新需要此工具 → 说明有人把标识符写回编号，先查那件事
```
**最后那句是重点：留理由不只是备忘，是留一个探测器。**

### 22.17 "已接受"必须写后果 + 触发复查条件

> **"已接受"必须写清"如果它发生，后果是什么"，并附触发复查条件。**
> **"接受"是一个决策，决策必须带后果；没有后果的"已接受"等于"没看见"。**

```
R12 · 科技树缩减至 24 节点 → 多周目差异变薄 —— 已接受
  后果：单局覆盖率 50–67%（原 39–52%），每局漏掉 33–50% 节点
  长期影响：第 2–3 周目后重复感上升
  触发复查条件：多周目留存率下降 / 玩家反馈出现"重复"
```
**"触发复查条件"把"已接受"从"永不再看"变成"满足条件就重看"。没有复查条件的"已接受"，两年后就是"没人记得为什么接受过"。**

## 23. 交付结语

19 轮，**24 处实质错误**（架构 9 / 设计 9 / 验收 6），分布：

| 形状 | 次数 | 对策 | 能否当门禁 |
|---|---|---|---|
| 从二维表取数 / 取错格子 / 行列不一致 | 13 | 写表达式 → 键名三段式 → M28 扫描 | 部分可 |
| 全称判断未验反例 | 5 | 反例搜索 | ❌ 只能审查 |
| 区间边界未算全 | 4 | 函数 + 完整边界 | ❌ 只能审查 |
| 选错定义后正确推导 | 1 | 先问定义该不该存在 | ❌ 只能审查 |
| 其他 | 1 | — | — |

**24 处没有一处是靠"更仔细"避免的**——全部是另一个人拿一个数、一个定义、或**一个错的错因**顶上来的。

> **所以这套东西能用，不是因为 v1.0 写得好，是因为它"能被挑"。**

按价值排序的真正产出：

1. **四层数值纪律 + 第 0 层写表达式**——从 24 处错里长出来的，能预测下次错在哪
2. **"跑一次型 / 每次要做型"分类**——决定哪些能当门禁、哪些只能当纪律
3. **`effect_sink` 唯一入口 + 零流消费纯 hash + `elapsed_ticks`**——把"越界""抽取顺序""时间漂移"三类 bug 从结构上消灭
4. **能消灭冗余就不要校验冗余**（C28，唯一一次做减法）
5. 引擎选型 / 目录 / 12 模块接口 / 存档 schema（底座，可替代）

**最后一句**：这套东西的验收标准是**"第一次跑至少红 2 条"**，不是"全绿即通过"。因为——

> **代码错了会崩，基线错了不会崩，只会让所有人按错的数干活，而且每一份产出都看起来对。**

### 24.1 第一层：数值内核（`proto/refcore.py`）

参考实现：状态契约（writers 白名单）+ `elapsed_ticks` 时基 + 四条状态 + 存档往返。

```
PASS  F0  时基常量双向校验
PASS  M1  推 10 GH → 43200 ticks 整数全等
PASS  M2  饥饿归零死亡 100±2 s            → 实测 100.017 s
PASS  M3  渴归零死亡 66.7 s 区间           → 实测 66.667 s
PASS  M2a 饥饿 100→0 恰好 20 GH
PASS  M2b 死亡后不再衰减
PASS  M7+P7 存档往返 diff=0
PASS  M8  反复存档文件数与路径不变
PASS  C1  UI 越权写 HP 被拒
PASS  C2  非时间系统推进时间被拒
合计 10/10
变异：3/3 被杀死，且每次只有目标判据变红
```

**第一次跑不是全绿——红的是 `M2a`。** 查下来红的不是实现，是**判据本身**：它同时测"饥饿速率"与"渴致死"，渴在 GH 14.3 先杀死玩家，饥饿自然停在 25。

> **这正是团队刚立的"多因判据必须拆"，在自己的第一条断言上应验了。** 拆开（钉住渴）后转绿，并补出 `M2b 死后不再衰减`——一条原本没人想到的隐含契约。

### 24.2 第二层：数据层源码判据（`tools/validate_data.py`）

**变异测试结果（关键）**：

| 变异 | 结果 |
|---|---|
| `stage_b_day_gh` 12→13 | **KILLED**（只有时间链红） |

> **F0-b 只防"文档手改秒值"，不防"帧数被改坏"。** 秒值由帧数生成后，两者永远一致——**这正是设计侧预判的恒绿形态**，现在有了实测证据。
